Agent 与 Function Calling

适用岗位：AI/Agent 开发（面试必问 + 场景设计） ｜ 形态：流程图 + JSON 示例 + 翻车清单 ｜ 更新：2026-09-30
要点速记：Agent 循环 = 目标 → 思考/规划 → 调工具 → 观察 → 迭代（ReAct = Reason + Act 交替，2022）；Function Calling 四步：给 Schema → 模型只出"函数名 + 参数 JSON" → 应用代码执行 → 结果回填继续——模型不执行、只出参；工具描述质量决定调用质量；翻车三件套：参数幻觉、死循环、错误不重试；MCP（2024）= 工具/上下文对接的标准协议。

一、知识点梳理

Agent 循环：给模型一个目标，它自主走"目标 → 思考/规划 → 选工具发起调用 → 拿到观察 → 判断是否完成 → 继续迭代"的循环，直到产出最终回答。代表范式 ReAct（2022）：Reason 与 Act 交替——把思考过程写出来再决定动作，工具/环境返回"观察"（Observation）回填继续推理；思考外化带来可解释性与可中途纠偏的能力。

目标 → 思考/规划 → 选工具 → 执行工具（应用侧） → 观察结果
        ↑                                        │
        └─────────── 未完成，继续迭代 ←───────────┘
                                     信息足够 ↓
                                   给出最终回答
flowchart LR
    A[目标] --> B[思考 规划]
    B --> C[选工具]
    C --> D[执行工具 应用侧]
    D --> E[观察结果]
    E --> F{信息足够吗}
    F -- 否 --> B
    F -- 是 --> G[给出最终回答]

Function Calling 完整流程（四步背熟）：

  • ① 开发者把工具列表（JSON Schema：名称、描述、参数类型、required）随请求发给模型；
  • ② 模型不执行，只输出调用意图：函数名 + 参数 JSON；
  • ③ 开发者的应用代码校验参数并真正执行——鉴权、限流、副作用控制都在这一层；
  • ④ 执行结果以 tool 消息回填对话，模型基于观察继续生成，或再发起下一轮调用。

职责边界一句话：模型负责决策与出参，应用负责执行与兜底——模型"自己脑补执行结果"就是幻觉。

// ① 开发者随请求注册工具列表（JSON Schema，节选）
{"tools": [{"type": "function", "function": {
    "name": "get_weather",
    "description": "查询指定城市与日期的天气",
    "parameters": {"type": "object",
        "properties": {"city": {"type": "string", "description": "城市名"},
                       "date": {"type": "string", "description": "YYYY-MM-DD"}},
        "required": ["city"]}}}]}
// ② 模型只输出调用意图（不执行！arguments 是字符串形式的 JSON）
{"tool_calls": [{"id": "c1", "type": "function",
    "function": {"name": "get_weather", "arguments": "{\"city\": \"杭州\"}"}}]}
// ③ 应用代码执行后，把结果以 tool 消息回填，继续对话
{"role": "tool", "tool_call_id": "c1", "content": "{\"temp\": 26, \"cond\": \"多云\"}"}
  • 工具描述质量决定调用质量：工具描述是写给模型看的接口文档——何时该用、参数含义、枚举取值、示例，写得越清楚调用越准；描述含糊是参数幻觉的温床。
  • 多工具编排与并行调用：相互独立的调用可以在一轮里并行发出（多个 tool_calls）；有依赖的必须等回填再串行发起；复杂流程由模型规划顺序或在代码侧编排。工具箱里最常见的一类工具是知识库检索——先捞相关资料再决策（见 RAG 从原理到落地）。

常见翻车：

翻车点现象工程防护
参数幻觉编造枚举外的取值、格式错、拿幻觉值硬调Schema 校验 + 枚举约束 + 把报错回填让模型自改
死循环同一工具反复调、不判断终止最大步数 / 预算上限 + 循环检测
错误处理差一次失败就放弃，或原样盲目重试错误分类处理，重试必须带上失败原因

MCP 一句话：MCP（Model Context Protocol，2024 年推出的开放协议）把"模型 ↔ 工具/数据源"的对接标准化——工具方按协议实现一次，多个 Agent 宿主都能接入，把 M×N 的对接变成 M+N。与 Function Calling 的关系：FC 是模型侧的调用机制，MCP 是工具生态侧的标准协议，两者互补。

二、考点说明

面试必问场景设计AI 岗笔试

  • Agent 循环五步默写 + ReAct 是什么（Reason+Act 交替、观察回填）。
  • Function Calling 四步流程 + "谁执行"的职责边界——最高频追问。
  • 给一个场景（查天气/查库/发工单）当场讲清 Agent 数据流。
  • 工具描述质量、并行调用与依赖编排、翻车点与工程护栏。
  • 追问：MCP 是什么、与 function calling 什么关系；记忆与上下文怎么管理。

三、示例题目（点击选项即时判分）

单选1. Function Calling 流程中，"真正执行函数"的是谁？（  ）

A. 模型在输出参数后自行调用函数并返回结果
B. 开发者的应用代码执行函数，把结果以 tool 消息回填给模型继续生成
C. 模型服务提供方会自动执行所有注册的函数
D. 不需要执行，模型会自己补全结果
答案 B。模型的职责止步于"理解工具列表 + 输出函数名与参数 JSON"的调用意图；执行、鉴权、副作用控制全部在应用侧；结果回填后模型才能基于真实观察继续。D 正是"幻觉执行结果"的典型错误。来源：面试高频改编。

单选2. ReAct 范式的核心机制是（  ）

A. 推理（Reason）与行动（Act）交替进行，行动后的观察回填再驱动下一轮思考
B. 只做任务规划，不与任何环境交互
C. 多个模型互相辩论、投票得出结论
D. 把所有工具一次性全部调用，汇总结果作答
答案 A。ReAct（2022）= Reason + Act：思考痕迹写出来再行动，观察是工具/环境的真实反馈，回填后继续推理直到完成。C 描述的是 debate 类多智能体玩法，D 是"乱枪打鸟"不是范式。来源：牛客经典题。

多选3. 关于 Agent 的组成与工程实践，正确的有（  ）

A. 规划：把目标拆成步骤、决定调用哪些工具、判断何时终止
B. 工具：模型只产出调用意图（函数名 + 参数 JSON），执行在应用侧
C. 记忆/上下文管理：历史对话与观察结果如何取舍、拼进上下文
D. 只要模型足够强，参数校验和最大步数限制都可以省掉
答案 ABC。D 是翻车根源——参数幻觉与死循环恰恰要靠"Schema 校验 + 最大步数/预算 + 错误回填"等工程护栏兜底，模型再强也不是理由。A、B、C 对应 Agent 三要素：规划、工具、记忆。来源：面试高频改编。

面试口述4. 设计一个"查天气"Agent，把完整数据流讲一遍。

参考回答① 注册工具：把 get_weather(city, date) 的 JSON Schema（参数类型、required、枚举说明）放进系统提示；② 用户问"明天杭州穿什么" → 模型思考需要先查天气 → 输出 tool_call：get_weather，参数 {"city": "杭州", "date": "2026-10-01"}；③ 应用侧校验参数（城市合法性、日期格式）→ 调天气 API → 结果以 tool 消息回填；④ 模型基于观察继续推理：气温 26℃、多云 → 生成穿衣建议；若用户还要比两个城市，可一轮并行发出多个 tool_calls。终止条件：模型判断信息足够即输出自然语言回答。加分：主动提参数校验、最大步数上限、失败重试策略——展示工程意识。来源：AI 岗笔试高频。

面试口述5. Agent 常见的翻车点有哪些？工程上怎么防？

参考回答① 参数幻觉——编造枚举外的取值、格式错：上 Schema 校验与枚举约束，出错把报错信息回填让模型自己改；② 死循环——同一工具反复调、不判停：设最大步数与预算上限，加循环检测；③ 错误处理差——一次失败就放弃或原样盲目重试：把错误分类（参数错 / 服务错 / 权限错）分别处理，重试必须带上失败原因。另一大根因是工具描述写得含糊——工具描述就是给模型看的接口文档，描述质量直接决定调用质量。加分：终止条件要在系统提示里写明（何时算完成、何时该停）。来源：面试高频改编。

四、易错点小结

① 模型永远不执行函数——答"模型自己调 API"直接暴露没做过落地；② arguments 是字符串形式的 JSON，应用侧要 parse + 校验后再执行；③ 并行调用要求工具间无依赖，有依赖必须串行等回填；④ 观察回填用的是 tool/工具消息角色，不是再发一条 user 消息；⑤ 死循环的根因常是"终止条件没讲清"——系统提示里写明何时停；⑥ MCP 是协议层标准化，FC 是模型能力层机制，两者不是竞争关系。
