进程同步与死锁

适用岗位：全部（PV 手算是笔试计算重灾区，死锁是面试常客） ｜ 形态：概念 + PV 计算 + 双语言代码 ｜ 更新：2026-09-30
要点速记：临界区四原则（空闲让进、忙则等待、有限等待、让权等待）；P(S) 减 1，减完 S<0 则阻塞，此时 |S| = 等待进程数，V(S) 加 1 后唤醒一个；死锁四个必要条件缺一不可，但"互斥"一般不可破坏；保证不死锁的最少资源数 m ≥ n(k−1)+1；死锁预防=破坏条件（保守），避免=银行家算法（动态判断安全状态），检测+解除=允许发生再撤销。

一、知识点梳理

同步 vs 互斥：互斥是"一次只许一个进程进临界区"（竞争关系），同步是"执行顺序有依赖，A 没做完 B 必须等"（协作关系）。信号量两种都能表达。

临界区访问四原则：空闲让进、忙则等待、有限等待（不能饿死）、让权等待（进不去就阻塞让出 CPU，而不是忙等）。

信号量与 PV：S 表示可用资源数。P(S)（wait）：S−=1，若 S<0 进程阻塞入等待队列；V(S)（signal）：S+=1，若 S≤0 唤醒一个等待者。整型信号量不满足让权等待，记录型（含阻塞队列）才满足。物理含义记法：S<0 时 |S| = 正在等待的进程数；S>0 时 S = 还可用资源数。

生产者—消费者（必背模板）：缓冲区容量 n，互斥信号量 mutex=1，同步信号量 empty=n（空槽数）、full=0（产品数）：

生产者:  P(empty); P(mutex); 放产品; V(mutex); V(full)
消费者:  P(full);  P(mutex); 取产品; V(mutex); V(empty)

两个 P 的顺序不能换：先 P(mutex) 再 P(empty)，缓冲区满时生产者会拿着锁去等空槽，消费者又拿不到锁，死锁；两个 V 的顺序随便换（不影响正确性）。

死锁四个必要条件：①互斥（资源一次一个用）；②请求并保持（抱着碗看着锅）；③不可剥夺（不能抢）；④循环等待（P0 等 P1 的、P1 等 P0 的……成环）。四个同时成立才可能死锁，破坏任意一个即可预防。

处理策略对比：

策略思路代价
预防静态破坏四条件之一（如一次性申请全部资源破坏"请求保持"，资源排序破坏"循环等待"）资源利用率低、吞吐低，但简单
避免动态判断，只在"安全状态"下分配——银行家算法每次分配都要算，需预知最大需求
检测+解除先放任，用资源分配图周期性检测，发现环再解除（剥夺/撤销进程）检测开销与解除损失

银行家算法思想一句话：假想满足某进程的最大需求并让它跑完归还资源，若所有进程都能按某个顺序依次跑完（找到安全序列），这次分配才安全；找不到安全序列就不分配。

死锁 vs 饥饿：死锁是互相等待成环、谁也动不了；饥饿是优先级低一直轮不到（可以独立存在，不构成环）。

代码模板（Java 用 Semaphore / Python 用 threading.Semaphore，同一套逻辑）：

Java 
import java.util.concurrent.*;

Semaphore mutex = new Semaphore(1);   // 互斥锁
Semaphore empty = new Semaphore(n);   // 空槽数，初值 n
Semaphore full  = new Semaphore(0);   // 产品数，初值 0

// 生产者线程
empty.acquire();  mutex.acquire();
queue.put(item);                      // 放产品
mutex.release();  full.release();

// 消费者线程
full.acquire();   mutex.acquire();
item = queue.take();                  // 取产品
mutex.release();  empty.release();
Python 
import threading

mutex = threading.Semaphore(1)
empty = threading.Semaphore(n)
full  = threading.Semaphore(0)

def producer():
    empty.acquire(); mutex.acquire()
    buffer.append(item)               # 放产品
    mutex.release(); full.release()

def consumer():
    full.acquire();  mutex.acquire()
    item = buffer.pop(0)              # 取产品
    mutex.release(); empty.release()
实际工程里 Java 直接用 BlockingQueue（内部已做好同步），Python 用 queue.Queue——手写 PV 是为了考试与理解，面试提一句工程封装是加分。

二、考点说明

笔试选择PV 计算面试口述

  • PV 计算：给信号量初值和一串 P/V 操作，问终值与阻塞/唤醒次数——核心口诀"P 减 V 加，S<0 的绝对值是等待人数"。
  • 给场景设信号量及初值（几把互斥锁、几个同步信号量、初值各是多少），并判断 P 操作顺序能否交换。
  • 死锁四条件识别与"破坏哪条可行/不可行"判断。
  • 最少资源数公式 m ≥ n(k−1)+1 的代入计算。
  • 面试：死锁三策略对比、银行家算法思想、工程上如何避免死锁（按序加锁、tryLock 超时、缩小锁粒度）。

三、示例题目（点击选项即时判分）

计算1. 信号量 S 初值为 3，进程对其执行了 4 次 P 操作和 2 次 V 操作。最终 S 的值与处于阻塞态的进程数是（  ）

A. S = 2，阻塞 0 个
B. S = 1，阻塞 0 个
C. S = −1，阻塞 1 个
D. S = 5，阻塞 0 个
答案 B。S = 3 − 4 + 2 = 1 > 0，表示还有 1 个可用资源，没有任何进程等待。只有 P 之后 S 变负才会阻塞，S = −1 时 |−1| = 1 个等待者。来源：408 统考高频题型（公开真题常考形式）。

单选2. 生产者—消费者问题中，生产者把两个 P 操作写成 P(mutex); P(empty);（先申请互斥锁再申请空槽）。当缓冲区已满时会发生（  ）

A. 什么也不发生，等 empty 出现即可
B. 生产者被饿死
C. 死锁：生产者持有 mutex 等空槽，消费者因拿不到 mutex 无法消费
D. 缓冲区被覆盖写
答案 C。持有互斥锁再去等资源，是对"请求并保持"条件的经典制造——同步信号量的 P 必须在互斥 P 之前。V 操作顺序交换不影响正确性。来源：408 统考高频题型（公开真题常考形式）。

多选3. 下列属于死锁必要条件的有（  ）

A. 互斥：资源同一时刻最多被一个进程占有
B. 可剥夺：资源可以被系统强行收回
C. 请求并保持：占有资源的同时又提出新的资源请求
D. 循环等待：等待关系构成环形链
答案 ACD。四条件是互斥、请求并保持、不可剥夺、循环等待；B 把"不可剥夺"说反了。破坏其中任意一条即可预防死锁，但互斥是资源本性（如打印机），通常破坏后三条。来源：408 统考高频题型（公开真题常考形式）。

计算4. 系统有 5 个进程，每个进程最多同时需要 2 台打印机。系统至少要配置多少台打印机才能保证不发生死锁？若每个进程最多需要 3 台呢？

先自己算，再展开对答案公式 m ≥ n(k−1)+1：最坏情况每个进程都拿到 k−1=1 台、还差最后 1 台，此时再有一台就能让某个进程凑齐跑完释放。5×(2−1)+1 = 6 台；每进程 3 台时 5×(3−1)+1 = 11 台。来源：408 统考高频题型（公开真题常考形式）。

面试口述5. 死锁的预防、避免、检测+解除三种策略怎么选？银行家算法的核心思想是什么？工程上你怎么避免死锁？

参考回答预防=静态破坏四条件之一（一次性申请全部资源、资源编号按序申请），安全但利用率低；避免=动态判断每次分配后是否仍是安全状态，代表是银行家算法——假想满足请求后能否找到一个"所有进程都能依次跑完并归还资源"的安全序列，找不到就不分配；检测+解除=放任发生，周期性用资源分配图找环，发现死锁再剥夺资源或撤销进程，利用率最高但有解除代价。工程实践：所有线程按固定顺序加锁（破坏循环等待）、用 tryLock 带超时失败重试、减小锁粒度和持锁时间、用无锁数据结构或消息队列化。

四、易错点小结

① S<0 时 |S| 才是等待进程数，S≥0 时没有等待者——别把正的 S 当"等待人数"；② 记录型信号量的 P 里阻塞才满足"让权等待"，整型信号量是忙等；③ 生产者消费者 P(empty)/P(full) 与 P(mutex) 顺序不能换，V 顺序无所谓；④ 死锁四条件是"必要"不是"充分充足"，成环不一定死锁（同类资源多实例时可能互相错开）；⑤ 死锁与饥饿：饥饿可以单进程发生，死锁至少两个且成环。
