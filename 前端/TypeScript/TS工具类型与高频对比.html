TS 工具类型与高频对比

适用岗位：前端（TS 笔试 + 面试必问） ｜ 形态：知识点 + 给类型问结果题（tsc 实跑核对） ｜ 更新：2026-09-30
要点速记：工具类型全家桶 Partial / Required / Readonly / Pick / Omit / Record / ReturnType / Parameters；底层三件套：keyof 取键联合、typeof 取值的类型、索引访问 T['a']；映射类型 [K in keyof T] 逐键改写——Partial<T> = { [K in keyof T]?: T[K] } 一行实现；泛型约束 extends 限定 T 的形状；TS vs JS 两连：类型擦除（编译后无类型、运行时不存在）与结构化类型（鸭子判断，看形状不看名字）。

一、知识点梳理

内置工具类型表（示例基于 interface User { name: string; age: number; id: number }）：

工具类型作用示例结果
Partial<T>全部属性变可选{ name?: string; age?: number; id?: number }
Required<T>全部属性变必填可选修饰符 ? 被移除
Readonly<T>全部属性变只读赋值后二次修改编译报错
Pick<T, K>从 T 中挑出 K 指定的键Pick<User,'name'|'age'> → { name; age }
Omit<T, K>从 T 中剔除 K 指定的键Omit<User,'id'> → { name; age }
Record<K, V>用键集合 K 构造 V 类型的键值对Record<'x'|'y', number> → { x: number; y: number }
ReturnType<F>取函数返回值类型() => string → string
Parameters<F>取函数参数为元组类型(a: string, b: number) => void → [string, number]

背后的底层语法三件套：keyof T 取键的联合（keyof User → 'name' | 'age' | 'id'）；typeof 变量 取该值的类型（与运行时 typeof 同名不同物，这是类型空间的运算符）；索引访问 User['name'] 直接取出属性类型。

映射类型与极简实现：[K in keyof T] 遍历键联合、对每个键做改写——内置工具类型多半就是几行映射类型：

TypeScript 
type Partial<T>  = { [K in keyof T]?: T[K] };   // 逐键加可选
type Readonly<T> = { readonly [K in keyof T]: T[K] };
type Pick<T, K extends keyof T> = { [P in K]: T[P] };

泛型约束 extends：限制 T 必须满足的形状，约束内可以使用被约束的成员：

TypeScript 
function pluck<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];          // K 被约束为 T 的键，编译通过
}

TS vs JS 面试对比：① 类型擦除——TS 只在编译期做静态检查，编译产物是纯 JS、类型全部消失，运行时不能依赖类型信息（判断得手写类型守卫），换来零运行时开销；② 结构化类型（鸭子判断）——赋值兼容只看形状不看声明名与继承关系：Point3D 的值可以直接赋给 Point2D（形状是子集），这正是"长得像就行"。反例细节：对象字面量直接赋值会触发"多余属性检查"（excess property check），多出的属性反而报错（tsc 实跑：TS2353）。

给类型问结果（tsc 5.5.4 strict 实跑核对）：Record<'x'|'y', number> 赋值 { x: 1, y: '2' } 报 TS2322；Readonly 对象二次赋值报 TS2540；Parameters 元组错位赋值报 TS2322；Point3D 值赋给 Point2D 类型通过。

二、考点说明

笔试类型推断面试必问

  • 笔试：给类型问结果（Record/Pick/Partial 组合的赋值正误）、哪几行编译报错。
  • 面试：unknown 为什么比 any 好、工具类型的实现原理（映射类型 + keyof）、TS 与 JS 的类型擦除与结构化差异。
  • 追问储备：Partial/Readonly 可叠加（建模"草稿→定稿"两阶段表单）；Omit 不校验键是否存在（实现细节）；excess property check 只对对象字面量直接赋值生效。

三、示例题目（点击选项即时判分）

单选1. 下面代码的编译结果是（  ）

TypeScript 
type T2 = Record<'x' | 'y', number>;
const w: T2 = { x: 1, y: '2' };  // 行①
A. 编译通过，y 的类型被拓宽为 string | number
B. 编译报错：Record 两个键都要求 number，y 是 string
C. 编译报错：Record 只接受 string 类型的键
D. 编译通过，y 被推断为 any
答案 B。tsc 5.5.4 strict 实跑：error TS2322: Type 'string' is not assignable to type 'number'（指 y）。Record<'x'|'y', number> 的结果是 { x: number; y: number }——字面量联合当键、同一类型当值，全部键都必须满足。来源：牛客经典题。

多选2. 关于工具类型的底层语法，正确的有（  ）

A. keyof User 的结果是 'name' | 'age' | 'id' 这样的键联合
B. Partial<T> 的极简实现是 { [K in keyof T]?: T[K] }
C. Parameters<F> 取到的是函数参数的元组类型
D. ReturnType<F> 是在运行时反射函数计算出来的
答案 ABC。工具类型全部是编译期的类型运算：映射类型 [K in keyof T] 逐键改写、索引访问 T[K] 取成员类型；类型擦除后运行时根本没有类型，D 错。来源：面试高频改编。

单选3. 下面代码行① 的编译结果是（  ）

TypeScript 
interface Point2D { x: number; y: number }
interface Point3D { x: number; y: number; z: number }
const p3: Point3D = { x: 1, y: 2, z: 3 };
const p2: Point2D = p3;  // 行①
A. 编译报错：两个 interface 名字不同不能互相赋值
B. 编译通过：TS 是结构化类型（鸭子判断），p3 的形状满足 Point2D
C. 编译报错：必须显式 as 断言
D. 编译通过，但运行时 TypeError
答案 B。tsc 实跑通过：TS 只看形状不看名字（鸭子判断），Point3D 拥有 Point2D 的全部成员所以兼容。注意细节：把对象字面量直接赋给 Point2D 会触发多余属性检查，{x,y,z} 里的 z 反而报 TS2353——多成员变量赋值可以，多成员字面量直接赋值不行。来源：面试高频改编。

报错定位4. 下面代码中哪几行编译报错？（  ）

TypeScript 
interface User { name: string; age: number }
const p: Partial<User> = {};               // 行①
p.name = 123;                              // 行②
const r: Readonly<User> = { name: 'A', age: 1 };  // 行③
r.name = 'B';                              // 行④
type P = Parameters<(a: string, b: number) => void>;  // 行⑤
const arr: P = [1, 'a'];                   // 行⑥
A. 仅行②④
B. 行②④⑥
C. 行①②④
D. 仅行⑥
答案 B。tsc 5.5.4 strict 实跑核对：行② TS2322（name?: string，不能赋 number）；行④ TS2540（Cannot assign to 'name' because it is a read-only property）；行⑥ TS2322（Parameters 元组是 [string, number]，错位赋值类型不符）。行① Partial 全可选、赋空对象合法；行③ Readonly 赋完整对象合法；行⑤ 只是类型声明。来源：牛客经典题。

面试口述5. unknown 为什么比 any 好？什么场景该用它？

参考回答any 是直接关闭类型检查：能随意访问任何成员、随意参与运算，错误会被"传染"到下游，IDE 补全也失效——等于把 TS 写回 JS。unknown 是"安全的 any"：什么值都能接收，但使用前必须收窄（typeof / in / 判等）或显式断言，把"这里的数据不可信"显式钉在类型上，编译器逼你先验后用，补全也正常。场景：JSON.parse 的返回、接口响应、第三方库没标类型的导出、catch 捕获的异常对象——凡是"来源不可信"的数据都该先接成 unknown，收窄后再用。加分点：unknown 赋值方向——任何值可赋给 unknown，但 unknown 赋给具体类型必须先收窄；never 是它的对偶（底类型，什么都不能赋）。来源：牛客经典题。

四、易错点小结

① Record 的键是字面量联合时，每个键都必须出现且类型一致；② Partial 与 Readonly 的实现靠映射类型 [K in keyof T]，面试能写出一行实现就是加分；③ 结构化类型只看形状——但对象字面量直接赋值会触发多余属性检查，多写的属性反而报错（tsc 实跑 TS2353）；④ 类型擦除后运行时没有类型，参数校验、类型守卫要手写；⑤ typeof 在类型空间取"值的类型"、keyof 取"类型的键"、T['a'] 取"属性的类型"，三者是工具类型的原料；⑥ 泛型约束 K extends keyof T 的意义：让 key 参数只能传真实存在的键。
