缓存穿透、击穿、雪崩与分布式锁

适用岗位：测开(Java)、通用软开、后端（项目场景题最常考） ｜ 形态：场景辨析 + 方案 + 代码 ｜ 更新：2026-09-30
要点速记：记忆锚点——穿透=查一个不存在的、击穿=一个热点 key 过期瞬间、雪崩=一批 key 同时过期或 Redis 整体宕机；一致性用 Cache Aside：先更新数据库再删除缓存（删除而非更新，懒加载+防并发乱序）；分布式锁三件套：SET key uniqueValue NX EX 一条命令原子加锁、值存唯一标识 + Lua 保证"判断+删除"原子、Redisson 看门狗自动续期。

一、知识点梳理

三大问题：定义 + 对策一张表（先辨析场景，再给方案）：

问题定义（一句话）典型场景对策
穿透查询根本不存在的数据，缓存永不命中，每次都打穿到数据库恶意请求 id=-1、爬虫乱撞①入口参数校验 ②缓存空值（短 TTL，防占内存）③布隆过滤器前置拦截
击穿某一个热点 key 过期的瞬间，海量并发同时打到数据库秒杀商品、爆款详情页缓存到期①互斥锁重建（只放一个线程查库回填，其余等待重试）②逻辑过期（不删除，值里带过期时间，发现过期后异步重建、先返回旧值）③热点数据永不过期
雪崩一大批 key 同时过期，或 Redis 整体宕机，流量全量砸向数据库0 点统一设置的批量缓存、机房故障①过期时间加随机抖动 ②Redis 高可用（主从哨兵 / Cluster）③限流、降级、熔断兜底 ④多级缓存（本地 + Redis）

布隆过滤器一句话：位数组 + k 个哈希函数；判定"不存在"必然准确、判定"存在"可能误判（哈希碰撞），标准版不支持删除——适合 key 集合相对稳定的防穿透场景。

缓存与数据库一致性：Cache Aside 模式（旁路缓存，最常用）：

  • 读路径：先读缓存，命中直接返回；未命中读数据库 → 回填缓存 → 返回。
  • 写路径：先更新数据库，再删除缓存（不是更新缓存！）。
  • 为什么"删除"而不是"更新"缓存：①懒加载——写多读少的 key，每次写都更新缓存是白算，删掉等真正被读时再回填；②并发写时"更新缓存"会乱序：两个写请求到达数据库的顺序与到达缓存的顺序可能相反，最终缓存里留下旧值；删缓存没有这种终态错误。
  • 为什么"先库后删"而不是"先删后更"：先删后更的坏窗口——删完到库更新完之间，读请求未命中就读到【旧库值】并回填旧缓存，之后长期脏（读快写慢，窗口大）；先库后删的坏窗口需要"读请求在库更新前读到旧值、又拖到删缓存之后才回填"，相当于读比写还慢，概率极小。
  • 延迟双删：删缓存 → 更新库 → 延迟几百毫秒再删一次，兜底上述极小窗口；只能改善，不能根治。
  • 定位一句话：缓存只能给最终一致；要强一致就别用缓存，或加锁串行化——得不偿失。

分布式锁（单机锁 synchronized 只锁 JVM 内，多实例部署必须用分布式锁）：

  • 原子加锁一条命令：SET lockKey uniqueValue NX EX 30——NX（不存在才设置）+ EX（过期时间）+ 唯一值一把设好。为什么必须一条命令：SETNX 和 EXPIRE 分两步，中间宕机锁就永久不过期 → 死锁。
  • 锁误删问题：A 业务超时，锁到期被 B 拿走；A 干完后直接 DEL 会删掉B 的锁。解法：值存唯一标识（UUID:线程ID），释放前先判断是不是自己的锁。
  • 为什么释放必须用 Lua："GET 比对 + DEL"是两步，GET 判断完恰好锁过期被 B 抢到，比对结果就失效了——Lua 脚本在 Redis 单线程中整体原子执行，判断+删除不可分割。
  • 续期问题：锁 30 秒、业务跑了 35 秒照样出事 → Redisson 看门狗 watchdog：默认锁 30s，每 1/3 时间（10s）检查一次，业务没结束就自动续满 30s。
  • 可重入与 RedLock 一句：Redisson 用 hash 结构（field=线程标识，value=重入次数）实现可重入；RedLock 多节点多数派方案业界争议大（Martin Kleppmann vs antirez），常规业务单主 + 哨兵 / Redisson 足够，别当银弹。
Java 
// 分布式锁最小可用版（Jedis 风格）：原子加锁 + Lua 原子释放
String token = UUID.randomUUID().toString();
// 一条命令同时带上 NX + EX + 唯一值，防止两步之间宕机造成死锁
String ok = jedis.set("lock:order", token, SetParams.setNx().ex(30));
if (!"OK".equals(ok)) { /* 获取失败：短暂重试或直接返回 */ }

// 释放：Lua 保证"判断是自己的锁 + 删除"两步原子执行
String lua =
    "if redis.call('get', KEYS[1]) == ARGV[1] then " +
    "  return redis.call('del', KEYS[1]) " +
    "else return 0 end";
jedis.eval(lua, Collections.singletonList("lock:order"),
                 Collections.singletonList(token));
// 生产建议直接用 Redisson：可重入 + 看门狗自动续期，省掉手写这些坑

三、示例题目（点击选项即时判分）

单选1. 电商详情页给爆款商品缓存设了 30 秒过期；过期瞬间该商品的上万 QPS 同时打到 MySQL。这属于哪种问题（  ）

A. 缓存穿透
B. 缓存击穿
C. 缓存雪崩
D. 缓存污染
答案 B。锚点对号：一个热点 key 过期瞬间高并发直打库=击穿；查不存在的数据=穿透；一批同时过期或整体宕机=雪崩。对策：互斥锁重建或逻辑过期。来源：牛客经典题。

多选2. 关于三大缓存问题的对策，正确的有（  ）

A. 布隆过滤器可以前置拦截"查不存在数据"的穿透请求
B. 给过期时间加随机抖动，可缓解一批 key 同时过期引发的雪崩
C. 互斥锁重建能防止热点 key 过期瞬间大量线程同时查库
D. 缓存空值应设置与正常数据相同的长 TTL，减少失效次数
答案 ABC。空值缓存只防穿透，且 TTL 要短（几十秒级）：空值长期占内存，且数据一旦真创建出来旧空值还会挡住正常读。D 的做法两头都亏。来源：面试高频改编。

单选3. Cache Aside 模式中，写路径采用"先更新数据库，再删除缓存"而非"更新缓存"，最主要的原因是（  ）

A. 更新缓存有写放大且并发写会乱序覆盖，删除后按需回填（懒加载）能保证终态取到最新值
B. 先删缓存后更数据库没有任何坏窗口
C. 数据库和缓存之间支持跨存储的事务
D. 删除缓存比更新缓存节省的只是一次网络请求
答案 A。懒加载省掉"写了没人读"的无效计算；并发写到达顺序不一致时更新缓存会留下旧值，删除没有终态错误。B 错——先删后更的窗口更大（读快写慢）。来源：JavaGuide 收录题型。

单选4. 释放分布式锁时用 Lua 脚本执行"判断值相等再删除"，原因是（  ）

A. Lua 脚本的执行速度比普通命令快
B. GET 比对与 DEL 两步在脚本内原子执行，防止锁恰好过期被他人抢走后误删
C. Redis 的普通命令不支持条件判断
D. Lua 脚本可以绕过 Redis 单线程模型的限制
答案 B。GET 完恰好在 DEL 前过期、锁被 B 拿走，此时再 DEL 就删了别人的锁——两步必须不可分割，Lua 在单线程里整体执行天然原子。D 说反了：Lua 正是借单线程才原子。来源：面试高频改编。

面试口述5. 项目里缓存和数据库的一致性是怎么保证的？说说完整方案。

参考回答用 Cache Aside：读——先读缓存，未命中读库回填；写——先更新数据库，再删除缓存。两个关键追问都能接住：为什么删除不更新——懒加载省无谓计算，且并发写更新缓存会乱序留旧值；为什么先库后删——先删后更的窗口里读请求会把旧库值回填缓存（读快写慢，概率大），先库后删要求"读比写还慢"才出错，概率极小，必要时加延迟双删兜底。最后主动定位：这套只能保证最终一致，业务要求强一致就不该上缓存。加分点：把删除缓存改成消息队列异步删、或 binlog 订阅（Canal）删缓存。来源：面试高频改编。

四、易错点小结

① 空值缓存 TTL 要短、布隆过滤器"说不存在必然准、说存在可能误判"；② 击穿锁的是"单个热点过期瞬间"，雪崩是"一批同时 / 整体宕机"，场景题先数"一个还是一批"；③ 删缓存不等于更新缓存：懒加载 + 防并发乱序，两个理由都说出来；④ 加锁必须 SET NX EX 一条命令；释放必须 Lua"判断+删除"原子，值存唯一标识防误删；⑤ 锁的过期时间不等于业务完成保证——长任务靠 Redisson 看门狗续期；⑥ 别把"缓存最终一致"说成强一致，主动交代边界反而是加分项。
