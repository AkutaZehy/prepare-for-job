AOP 动态代理与 @Transactional 失效

适用岗位：测开(Java)、通用软开（事务失效场景题高频） ｜ 形态：原理 + 对比表 + 代码排查 ｜ 更新：2026-09-30
要点速记：AOP 五词——切面/连接点/切点/通知（@Around 环绕最强）/织入；JDK 动态代理基于接口（Proxy+InvocationHandler 反射），CGLIB 生成子类字节码（final 类/方法无法代理）；SpringBoot 2.x 起默认一律 CGLIB；@Transactional 本质是 AOP 环绕通知：开事务→执行→提交/回滚；失效八大场景必背——自调用（this 不走代理，最高频）、非 public、catch 吞异常、受检异常默认不回滚、类没被 Spring 管理、多线程、传播行为设错、存储引擎不支持。

一、知识点梳理

AOP 五词表（横切关注点模块化）：

术语含义
切面 AspectPointcut + Advice 组合成的横切逻辑模块（一个切面类）
连接点 JoinPoint程序执行中可被拦截的点；Spring AOP 里就是方法执行
切点 Pointcut匹配连接点的表达式，如 execution(* com.demo.service..*.*(..))
通知 Advice做什么+何时：@Before / @After / @AfterReturning / @AfterThrowing / @Around（环绕最强：可控是否执行、包裹前后逻辑、改返回值）
织入 Weaving把切面应用到目标对象生成代理的过程；Spring 是运行期动态代理织入（AspectJ 是编译期/类加载期字节码织入——对比加分）

两种动态代理对比：

维度JDK 动态代理CGLIB
原理基于接口：Proxy.newProxyInstance + InvocationHandler 反射调用目标方法继承目标类生成子类字节码（ASM），重写方法拦截（MethodInterceptor）
前提目标必须实现接口类可继承；final 类 / final 方法 / private 方法无法代理（不能重写）
Spring 口径传统 Spring：目标有接口默认 JDK无接口时用 CGLIB；proxy-target-class=true 强制 CGLIB；SpringBoot 2.x 起默认一律 CGLIB（注明版本）

AOP 典型应用：统一日志、权限校验、声明式事务、接口幂等防重、方法耗时监控。

@Transactional 原理一句话：本质是 AOP 环绕通知——方法执行前开启事务（取连接、setAutoCommit(false)），业务正常结束则提交，抛出 RuntimeException / Error 才回滚（默认不含受检异常，需 rollbackFor）。理解了"代理"，八大失效场景全都推得出来：凡是绕过代理、让切面看不到异常、或拿不到同一连接的，事务就失效。

失效八大场景表（必背）：

#场景为什么失效
①同类自调用（最高频）：this.method() 调本类事务方法this 不走代理对象，事务通知根本没机会执行
②方法非 publicSpring 事务切面只对 public 方法生效，非 public 拿不到事务属性
③异常被 try-catch 吞掉切面感知不到异常，方法"正常"结束，照常提交
④抛受检异常默认不回滚默认只回滚 RuntimeException 和 Error；IOException 这类要 @Transactional(rollbackFor = Exception.class)
⑤类没被 Spring 管理（自己 new 的）对象不是容器里的 bean，压根没有代理
⑥多线程调用事务绑定 ThreadLocal 里的同一个 Connection，新线程拿不到，子线程操作不在事务内
⑦传播行为设置错NOT_SUPPORTED 挂起事务以非事务运行；NEVER 遇到事务反而抛异常
⑧存储引擎不支持事务MyISAM 无事务，要 InnoDB

自调用的三种解法：①注入自身代理——@Autowired @Lazy 注入自己，调 self.method()（走代理才生效）；②AopContext.currentProxy()——启动类加 @EnableAspectJAutoProxy(exposeProxy = true)，方法内 ((OrderService) AopContext.currentProxy()).save()；③拆到另一个类——最朴素也最推荐，从设计上消除自调用。

传播行为三巨头：

传播行为规则典型用途
REQUIRED（默认）当前有事务就加入，没有就新建绝大多数业务方法
REQUIRES_NEW挂起当前事务，新开独立事务；内层回滚与否不影响外层已提交的部分（反之亦然）操作日志、审计——"日志失败不影响主业务"（外层还要 catch 住内层抛出的异常）
NESTED嵌套事务，靠 savepoint：内层回滚回到保存点、外层可捕获继续；外层回滚则内层必然回滚（同一物理事务）批量导入的分组容错

其余（SUPPORTS / MANDATORY / NOT_SUPPORTED / NEVER）知道"存在且可能把事务变非事务"即可。

SpringMVC 请求流程（文字版）：请求 → DispatcherServlet（前端控制器，统一入口）→ 查 HandlerMapping 得到执行链（Handler + 拦截器）→ HandlerAdapter 按适配规则调用（参数解析、数据绑定）→ Controller 执行业务返回 ModelAndView → ViewResolver 解析视图 → 渲染输出响应。前后端分离时：Controller 标 @ResponseBody（或 @RestController），返回值不走视图解析，由 HttpMessageConverter（Jackson）直接序列化成 JSON 写进响应体。

Java 
@Service
public class OrderService {
    @Autowired
    private OrderMapper orderMapper;

    // 失效①：同类自调用 —— this.savePoint() 不经过代理，事务不生效
    public void createOrder(Order o) {
        orderMapper.insert(o);
        savePoint();                        // ← 无事务保护！
    }

    @Transactional
    public void savePoint() { /* 加积分 */ }

    // 解法：注入自身代理，改走代理对象
    @Autowired @Lazy
    private OrderService self;

    public void createOrder2(Order o) {
        orderMapper.insert(o);
        self.savePoint();                   // ← 走代理，事务生效
    }

    // 失效④：默认只回滚 RuntimeException，受检异常要显式声明 rollbackFor
    @Transactional(rollbackFor = Exception.class)
    public void importUsers(List<User> users) throws IOException {
        for (User u : users) { persist(u); }   // 抛 IOException 也能回滚
    }
}

代理在 Bean 生命周期"BeanPostProcessor 后置"那一步生成——前后因果见同目录 SpringBoot核心IoC与Bean。

二、考点说明

笔试选择面试必问

  • 笔试：JDK/CGLIB 选择口径（有无接口 + Boot 版本）、失效场景判断、传播行为语义、MVC 流程排序。
  • 面试："说几种 @Transactional 失效场景"（按八大场景背，自调用必打头阵）、"自调用怎么解决"（三招）、"REQUIRED 和 REQUIRES_NEW 区别"、"项目里 AOP 用在哪"。
  • 追问链：代理生成时机 → 自调用失效 → exposeProxy → 传播行为 → 异常回滚规则，一环扣一环。

三、示例题目（点击选项即时判分）

单选1. SpringBoot 2.x 项目里，无接口的 UserService 被 @Transactional 增强，实际使用的代理方式是（  ）

A. JDK 动态代理，因为 Spring 默认优先 JDK
B. CGLIB 子类代理——SpringBoot 2.x 起默认 proxy-target-class=true，一律 CGLIB
C. AspectJ 编译期织入
D. 不生成代理，直接反射调用
答案 B。传统 Spring 才是"有接口默认 JDK、无接口 CGLIB"；SpringBoot 2.x 起默认一律 CGLIB（有接口也一样）。AspectJ 是另一种织入方式，Spring 默认不用。来源：面试高频改编。

多选2. 下列会导致 @Transactional 失效的有（  ）

A. 同类中通过 this 调用带 @Transactional 的方法
B. 事务方法声明为 private
C. 方法内 try-catch 把异常吞掉后正常返回
D. 方法为 public，抛出 RuntimeException 且未被捕获
答案 ABC。自调用绕过代理、非 public 拿不到事务切面、catch 吞异常让切面看不到——全失效。D 是事务正常回滚的标准姿势（RuntimeException 在默认回滚范围内）。来源：牛客经典题。

单选3. 下单主事务中要写操作日志，要求"日志写失败不影响下单主流程"，日志方法的传播行为与配套处理应是（  ）

A. REQUIRED，让日志加入主事务，一起提交一起回滚
B. REQUIRES_NEW 新开独立事务，外层再 try-catch 住日志方法的异常
C. NESTED，内层回滚时外层事务整体回滚
D. NEVER，禁止日志在事务中运行
答案 B。REQUIRES_NEW 让日志事务独立提交/回滚；但内层回滚抛出的异常若传到外层仍会带崩主事务，所以要配 try-catch。REQUIRED 会绑死主事务（D 语义完全不符）；NESTED 下外层回滚内层跟着没。来源：JavaGuide 收录题型。

单选4. SpringMVC 中一次请求的正确处理顺序是（  ）

A. DispatcherServlet → HandlerMapping → HandlerAdapter → Controller → ViewResolver
B. DispatcherServlet → HandlerAdapter → HandlerMapping → Controller → ViewResolver
C. HandlerMapping → DispatcherServlet → Controller → HandlerAdapter → ViewResolver
D. DispatcherServlet → Controller → HandlerMapping → HandlerAdapter → ViewResolver
答案 A。前端控制器先收口 → 查映射找 Handler（含拦截器链）→ 适配器执行（参数绑定、调 Controller）→ 拿到 ModelAndView → 视图解析渲染。前后端分离时最后一步换成 HttpMessageConverter 序列化 JSON。来源：牛客经典题。

面试口述5. 说出至少三种 @Transactional 失效场景，并给出自调用的解法。

参考回答先给总纲：事务靠 AOP 代理实现，绕过代理、切面看不到异常、拿不到同一连接，都会失效。然后挑最有把握的说：①同类自调用——this 不走代理，最高频；②方法非 public——切面只对 public 生效；③异常被 try-catch 吞掉——切面感知不到照常提交；④抛受检异常默认不回滚——默认只认 RuntimeException/Error，要 rollbackFor；⑤多线程——事务绑在 ThreadLocal 的连接上，子线程不在事务内。自调用三解：注入自身代理调 self 方法；@EnableAspectJAutoProxy(exposeProxy=true) 后用 AopContext.currentProxy()；或把方法拆到另一个 bean。加分点：顺手说出总纲的那句"凡是绕过代理的都失效"，展示体系而非背题。来源：面试高频改编。

四、易错点小结

① 事务失效排查顺序定式：是不是 Spring bean → 方法是不是 public → 有没有自调用 → 异常类型对不对（默认只回滚 RuntimeException/Error）→ 传播行为与存储引擎；② CGLIB 对 final 类/final 方法/private 方法直接无法代理——代理失效排查也要看这里；③ "REQUIRES_NEW 内层失败不影响外层"只对了半句——内层回滚抛出的异常传到外层照样回滚，必须配 try-catch；④ JDK 代理基于接口、CGLIB 基于继承，SpringBoot 2.x 起默认一律 CGLIB——版本口径别说混；⑤ 事务在哪个线程开启就只管哪个线程，跨线程的 SQL 不在同一事务里。
