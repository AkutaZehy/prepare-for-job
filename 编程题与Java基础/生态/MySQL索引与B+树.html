MySQL 索引与 B+ 树

适用岗位：测开(Java)、通用软开、AI 开发 ｜ 形态：概念 + SQL 分析 + 估算计算 ｜ 更新：2026-09-30
要点速记：B+ 树一句话 =矮胖（非叶不存数据、扇出大）+ 叶子有序链表（范围查询顺链扫）；InnoDB 二级索引叶子只存主键，查其他列要回表，查询列全在索引里=覆盖索引免回表；联合索引最左前缀：等值连续才延续，遇到范围就断；explain 的 type 到 range 及以上算合格，ALL 全表扫描要警惕；主键建议自增，避免随机插入导致页分裂。

一、知识点梳理

为什么用 B+ 树（对比表 + 一张结构示意）

候选结构问题B+ 树怎么赢
哈希表等值查询快，但不支持范围查询与排序叶子有序 + 链表，BETWEEN、ORDER BY 顺链走
二叉搜索树 / 红黑树二叉扇出只有 2，百万数据树高 20 层上下，树高≈磁盘 IO 次数一个节点一页（16KB），扇出上千，3 层搞定千万行
B 树非叶节点也存数据 → 单页放的键少 → 扇出小、树更高；范围查询要中序回溯非叶只存键+指针，扇出更大更矮；数据全在叶子且叶子成链表
有序数组查询快但插入删除要整体挪动增删只动叶子页，写放大可控
                [ 30 ]                     根/内节点：只存键 + 指针，不存整行数据
             /        \
      [10 | 20]     [40 | 50]            中间层：键 + 指针，一页 16KB 放上千键 → 扇出大、树矮
      /   |   \     /   |   \
   叶子页 叶子页 叶子页 叶子页 …            叶子层：存数据（聚簇）或主键（二级），键有序
     ⇆      ⇆      ⇆      ⇆             叶子间双向链表 → 范围/排序查询顺着链扫
一句话总结：矮胖树把磁盘 IO 压到 3 次以内 + 叶子有序链表天然支持范围查询。

聚簇索引 vs 二级索引

  • 聚簇索引：InnoDB 的主键索引。表本身就是一棵按主键组织的 B+ 树，叶子节点存整行数据——索引即数据。
  • 二级索引（辅助索引）：叶子节点存"索引列值 + 主键值"，不是行地址。
  • 回表：走二级索引只拿到主键值，要查的列不在索引里，就得拿主键回聚簇索引再查一次整行。
  • 覆盖索引：查询的列全部包含在所用的索引里，无需回表（explain 的 Extra 显示 Using index）。建联合索引很多时候就是为了造覆盖索引。
  • 对照：MyISAM 是非聚簇——主键索引与二级索引结构相同，叶子都存数据文件的地址偏移。
SQL 
-- user 表：id 主键自增，name VARCHAR，age INT
-- 二级索引 idx_name(name)

-- 走 idx_name 找到 name='tom' 的主键，再回聚簇索引取 age → 回表
SELECT id, age FROM user WHERE name = 'tom';

-- 要查的列（id）就在二级索引叶子里 → 覆盖索引，不回表
SELECT id FROM user WHERE name = 'tom';

最左前缀原则（联合索引 idx_abc(a, b, c)，逐条对照）

WHERE / ORDER 条件索引使用情况
a = 1 AND b = 2 AND c = 3a、b、c 全部生效
a = 1 AND b = 2a、b 生效
a = 1只有 a 生效
b = 2 / c = 3 / b = 2 AND c = 3用不上该索引（缺最左 a）
a = 1 AND c = 3只有 a 生效（c 断档）；MySQL 5.6 起可用索引下推 ICP 在索引层先过滤 c，减少回表
a = 1 AND b > 2 AND c = 3a、b 生效；范围列 b 之后的 c 停止匹配
a = 1 ORDER BY b, ca 定位后按索引序直接返回，避免 filesort
口诀：从最左列开始连续匹配，等值可以一直延续，遇到范围（>、<、BETWEEN）就断。

索引下推 ICP 一句话：MySQL 5.6 起，把 WHERE 中属于索引列的过滤条件下推到存储引擎，在二级索引上先过滤再回表，减少回表次数（Extra 显示 Using index condition）。

索引失效高频场景

SQL 
-- 假设：联合索引 idx_name_age(name, age)，name 是 VARCHAR

-- ① 前导通配：like '%son' 失效；前缀匹配 'ja%' 可以走
SELECT * FROM user WHERE name LIKE '%son';   -- 失效
SELECT * FROM user WHERE name LIKE 'ja%';    -- 正常走索引

-- ② 对索引列用函数或参与运算：失效；把运算挪到常量一侧
SELECT * FROM user WHERE UPPER(name) = 'TOM';  -- 失效
SELECT * FROM user WHERE id + 1 = 10;          -- 失效
SELECT * FROM user WHERE id = 9;               -- 修正

-- ③ 隐式类型转换：name 是 VARCHAR 却传数字，等价于对 name 做 CAST → 失效
SELECT * FROM user WHERE name = 1001;          -- 失效
SELECT * FROM user WHERE id = '5';             -- id 是 INT，'5' 转数字，不失效

-- ④ or 两侧只要有一侧无索引，整体不走索引
SELECT * FROM user WHERE name = 'tom' OR city = 'bj';   -- city 无索引，失效
  • 失效清单：① 索引列上用函数或参与运算；② 隐式类型转换（字符串列传数字失效，数字列传字符串不失效——方向别背反）；③ like 前导通配 '%x'；④ or 两侧有非索引列；⑤ 不满足最左前缀；⑥ 优化器判断全表扫描更快（二级索引选择性差、回表行数太多时，宁可全表）。

explain 的 type：从优到差

system > const > eq_ref > ref > range > index > ALL
system/const：主键或唯一键等值，最多一行；eq_ref：join 时用主键/唯一索引；ref：普通二级索引等值；range：索引范围扫描；index：扫整棵索引树；ALL：全表扫描。一般要求优化到 range 及以上算合格，出现 ALL 就要问一句为什么。

主键为什么建议自增

  • 自增主键的插入永远在 B+ 树最右叶子追加，页写满才开新页，顺序写、页利用率高。
  • 随机主键（如 UUID）插入点随机 → 频繁页分裂、产生碎片、缓存命中率下降。
  • 另外二级索引叶子都存主键副本，主键越短，所有二级索引越小——这也是主键常用 bigint 而非长字符串的原因。

三、示例题目（点击选项即时判分）

多选1. 表上有联合索引 idx(a, b, c)，下列哪些 SQL 能利用该索引？（  ）

A. WHERE a = 1 AND b = 2 AND c = 3
B. WHERE b = 2 AND c = 3
C. WHERE a = 1 AND b > 2 AND c = 3
D. WHERE a = 1 ORDER BY b, c
答案 ACD。B 缺最左列 a，用不上；C 用到 a、b——b 是范围列，其后的 c 断档失效，但索引本身走了；D 用 a 定位后按索引序输出，还免了 filesort。口诀：最左优先、连续等值可延续、遇范围即断。来源：面试高频改编。

单选2. 表 user 上有二级索引 idx_name(name)，执行 SELECT id FROM user WHERE name = 'tom'; 不需要回表，原因是（  ）

A. id 是主键，MySQL 规定主键查询永不回表
B. 二级索引叶子节点存的就是"name + 主键值"，SELECT 的列全在索引里，属于覆盖索引
C. MySQL 会自动把 name 索引升级为聚簇索引
D. 因为 id 是自增主键，天然有序，直接扫索引即可
答案 B。InnoDB 二级索引叶子存"索引列值 + 主键值"，查 id 恰好被覆盖（explain Extra 会显示 Using index）。A 的理由是错的——主键查询照样可能回表，比如 SELECT * FROM user WHERE id = 5 反而就是在聚簇索引上直接取。来源：牛客经典题。

多选3. 下列哪些写法会导致索引失效？（  ）

A. WHERE UPPER(name) = 'TOM'（name 有索引）
B. WHERE name = 1001（name 是 VARCHAR）
C. WHERE name LIKE 'tom%'
D. WHERE name = 'tom' OR city = 'bj'（city 无索引）
答案 ABD。A 对索引列用函数；B 隐式类型转换（VARCHAR 列传数字，等价于对 name 做 CAST）；D or 混入无索引列导致整体放弃索引。C 前缀匹配可以走索引——失效的是前导通配 '%tom'。来源：JavaGuide 收录题型。

计算4. 按业内常用估算口径（InnoDB 页 16KB；主键 bigint 8B + 页指针 6B，非叶节点扇出约 1200；叶子页每行约 1KB 即每页 16 行），一棵三层的 B+ 树大约能存多少行？（  ）

A. 约 200 万行
B. 约 2000 万行
C. 约 2 亿行
D. 约 200 亿行
答案 B。非叶每页可放 16384 ÷ (8+6) ≈ 1170，取扇出约 1200；三层 = 根 + 中间层 + 叶子层，叶子页数 ≈ 1200 × 1200 = 144 万，每页 16 行 → ≈ 2304 万，业内常口径为"三层 B+ 树约 2000 万行"。引申：这意味着一次主键查询最多 3 次页 IO，根与中间层常驻内存后实际 1~2 次。来源：面试高频改编。

单选5. 一条慢查询的 EXPLAIN 里 type 显示 ALL，说明什么、普遍的优化底线是什么？（  ）

A. 全表扫描；一般要求优化到 range 及以上算合格
B. 索引全扫描，是性能最好的访问方式
C. 主键等值查询，最多返回一行
D. 用了覆盖索引，无需回表
答案 A。type 从优到差：system > const > eq_ref > ref > range > index > ALL。ALL 是全表扫描，index 是扫整棵索引树（也没好到哪去），底线是优化到 range 及以上。出现 ALL 先看条件是否失效（函数/隐式转换/前导通配/or/最左前缀），再看要不要补索引。来源：面试高频改编。

面试口述6. 为什么 MySQL（InnoDB）选 B+ 树做索引结构，而不用 B 树、哈希或红黑树？

参考回答分四步对比：① vs 哈希：等值查询 O(1) 很快，但不支持范围查询和排序，数据库里 BETWEEN、ORDER BY、前缀匹配都是高频操作。② vs 红黑树/二叉搜索树：二叉结构扇出只有 2，百万行数据树高 20 层上下，每层一次磁盘 IO，磁盘是按页读的，矮树才省 IO；B+ 树一个节点就是一页 16KB，能放上千个键，扇出上千，三层就能装约 2000 万行。③ vs B 树：B 树非叶节点也存数据，单页能放的键更少、扇出更小、树更高；而且范围查询要中序遍历上下反复跳。B+ 树把数据全放叶子、非叶只存键，非叶一次 IO 带回更多键；叶子之间是双向有序链表，范围查询顺着链扫就行。④ vs 有序数组：查询二分很快，但插入删除要整体挪动，不适合频繁写入。总结：B+ 树 = 矮胖降 IO + 叶子有序链表撑范围查询。加分点：报出三层 2000 万的估算、回表/覆盖索引、自增主键避免页分裂。

四、易错点小结

① 判断联合索引是否生效：从最左列开始逐列对，等值连续才延续，遇到范围就断——"a=1 AND c=3"只有 a 生效。② '%x' 前导通配失效，'x%' 可以走，别一刀切说 like 失效。③ 隐式转换方向：字符串列传数字失效，数字列传字符串不失效。④ 回表是"二级索引 → 主键 → 聚簇索引"两次查找；SELECT * 是回表大户，按需取列或补覆盖索引。⑤ 主键用 UUID 的两个代价：页分裂 + 所有二级索引变大（叶子都存主键副本）。⑥ type=index 不是好信号——那是扫整棵索引树，底线是 range 及以上。
