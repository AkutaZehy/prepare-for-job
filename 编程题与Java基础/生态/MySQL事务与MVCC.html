MySQL 事务与 MVCC

适用岗位：测开(Java)、通用软开、后端（数据库八股头号高频） ｜ 形态：原理 + 对比表 + 场景分析 ｜ 更新：2026-09-30
要点速记：ACID 靠什么——原子性 undo log、持久性 redo log、隔离性 锁+MVCC、一致性是目的；InnoDB 默认可重复读（RR）；MVCC 三件套 = 隐藏列（trx_id/roll_ptr）+ undo log 版本链 + ReadView，RC 每次快照读新建 ReadView、RR 只在第一次建立——这就是两级别差异的全部根源；幻读是"部分解决"：快照读靠 MVCC、当前读靠间隙锁；行锁基于索引，条件无索引会升级为扫描加锁近表锁。

一、知识点梳理

ACID 与实现手段（面试常问"各自靠什么保证"）：

特性含义靠什么保证
原子性 A事务内操作要么全成功、要么全不执行undo log：回滚时按反向操作把数据改回去
持久性 D提交后的修改永久生效redo log：WAL 先写日志再刷数据页，崩溃后重放恢复
隔离性 I并发事务互不干扰锁 + MVCC：写写靠锁，读写靠版本链无锁并发
一致性 C数据从一个一致状态到另一个一致状态是目的不是手段：由 A/I/D 加应用层约束共同达成

并发三读：脏读=读到别的事务【未提交】的数据（A 把余额 100 改 200 未提交，B 读到 200，A 回滚，200 就是脏数据）；不可重复读=同一事务内两次读【同一行】值不同——侧重别的事务 update 改了值；幻读=同一事务内两次【同条件】范围查询行数不同——侧重别的事务 insert 多出了行。

四种隔离级别与现象矩阵：

隔离级别脏读不可重复读幻读说明
读未提交 RU可能可能可能性能最好，基本不用
读已提交 RC避免可能可能Oracle / PostgreSQL 默认
可重复读 RR避免避免部分解决MySQL InnoDB 默认；靠 MVCC + 间隙锁
串行化避免避免避免读加共享锁，完全串行，性能最差

注：SQL 标准里 RR 并不防幻读；InnoDB 用 MVCC + 临键锁把幻读做到了"部分解决"（准确说法见下）。

MVCC 三件套（多版本并发控制，只在 RC/RR 下生效）：

  • 隐藏列：每行记录带 trx_id（最近一次修改它的事务 id）、roll_ptr（回滚指针，指向 undo log 中的上一个版本）；无主键时另有 row_id。
  • undo log 版本链：每次更新把旧版本写入 undo log，roll_ptr 把历史版本串成链——MVCC 的"多个版本"就存在这条链上。
  • ReadView 四字段：m_ids（生成时刻所有活跃未提交事务的 id 列表）、min_trx_id（活跃中的最小值）、max_trx_id（系统下一个将分配的事务 id）、creator_trx_id（当前事务自己）。
  • 可见性判断一句话版：拿版本链上某版本的 trx_id 从新往旧问——等于 creator_trx_id（自己改的）可见；< min_trx_id（视图建立前已提交）可见；≥ max_trx_id（视图建立后才开启）不可见；介于两者之间：落在 m_ids 里不可见、不在则可见；不可见就顺 roll_ptr 看上一版本再问，直到找到可见版本。
  • RC 与 RR 的唯一实现差异：RC 每次快照读都新建 ReadView，能看到别的事务最新提交的值 → 不可重复读；RR 只在第一次快照读时建立 ReadView 并全程复用，整个事务一个视图 → 可重复读。背下这句，"为什么 RC 不可重复读"自然答得出。

快照读 vs 当前读：普通 SELECT 是快照读，读 MVCC 版本链、不加锁；当前读读最新已提交版本并加锁，包括 SELECT ... FOR UPDATE、SELECT ... LOCK IN SHARE MODE、UPDATE、DELETE、INSERT。RR 幻读"部分解决"的准确说法：纯快照读靠 MVCC 避免幻读；当前读靠临键锁（记录锁+间隙锁）锁住区间禁止插入。但两者混用仍有窗口——第一次快照读建好视图后，别的事务插入并提交，本事务若先当前读（比如 UPDATE 那条新行，把它的 trx_id 改成自己）再快照读就能看到它，幻读发生。所以只说"部分解决"，不说"解决"。

SQL 
-- RR 下"快照读 / 当前读混用仍见幻读"的复现（T1、T2 交错执行）
-- T1: START TRANSACTION;
-- T1: SELECT * FROM t WHERE id > 15;          -- 快照读：建立 ReadView，只见 id=20 一行
-- T2: INSERT INTO t VALUES (18, 'x'); COMMIT;  -- 别的事务插入并提交
-- T1: UPDATE t SET v='y' WHERE id = 18;        -- 当前读：新行 trx_id 被改成 T1 自己
-- T1: SELECT * FROM t WHERE id > 15;           -- 快照读：id=18 的 trx_id=自己 → 可见，幻读出现

三大日志对比：

日志所属层类型作用
redo logInnoDB 引擎层物理日志（"某页某处改成了什么"），循环写崩溃恢复重放，保证持久性（WAL）
undo logInnoDB 引擎层逻辑日志（反向操作）回滚保证原子性 + 支撑 MVCC 版本链
binlogServer 层逻辑日志（语句/行），追加写主从复制、数据恢复与备份

两阶段提交一句话：redo log 先置 prepare → 写 binlog → redo log 再 commit；保证 redo 与 binlog 两份日志一致，否则崩溃恢复后主从数据不一致。

锁体系（InnoDB）：全局锁（FTWRL，全库逻辑备份用）；表级——表锁、MDL 元数据锁（防 DML 撞 DDL）、意向锁 IS/IX（加行锁前先在表级打标记，让"能否上表锁"不必逐行检查，知道概念即可）、AUTO-INC 锁；行级锁三种——记录锁 Record Lock（锁单条索引记录）、间隙锁 Gap Lock（锁两条记录之间的开区间，只防插入）、临键锁 Next-Key Lock（记录+间隙，左开右闭，RR 下当前读的默认加锁单位）。行锁基于索引：WHERE 条件没走索引时走全表扫描，扫过的每一行都加锁，效果近似锁表（索引原理见同目录 MySQL索引与B+树）。

三大范式：1NF 列原子不可再分（反例：地址列塞"省-市-详址"，没法按市查询）；2NF 消除非主属性对联合主键的部分依赖（反例：(学号,课程号,姓名,成绩) 中姓名只依赖学号 → 把学生信息拆出去）；3NF 消除传递依赖（反例：(学号,系名,系主任) 中 学号→系名→系主任 → 把系信息拆出去）。

三、示例题目（点击选项即时判分）

单选1. 事务 A 两次执行 select * from t where age > 18，期间事务 B 插入一行 age=20 并提交，A 第二次查询多出一行。该现象及它在 InnoDB 默认隔离级别下是否可能出现，正确的是（  ）

A. 脏读；RR 下完全避免
B. 幻读；RR 下仍可能出现（部分解决）
C. 不可重复读；RR 下仍可能出现
D. 幻读；RR 下完全避免
答案 B。两次同条件查询行数变化是幻读（不可重复读强调"同一行的值变了"）。InnoDB RR 只是把幻读部分解决：纯快照读靠 MVCC、当前读靠临键锁；快照读与当前读混用仍有窗口。来源：牛客经典题。

单选2. RC 隔离级别能读到别的事务最新已提交的数据，而 RR 不能。其根本原因是（  ）

A. RC 不使用 MVCC，直接读最新行
B. RC 下没有 undo log 版本链
C. RC 每次快照读都新建 ReadView，RR 只在第一次快照读时建立并全程复用
D. RR 对全表加了共享锁
答案 C。两个级别都用 MVCC（隐藏列、版本链一个不少），差别只在 ReadView 的生成时机：RC 每次快照读新建 → 看得到最新提交；RR 复用第一次的 → 全程一个视图。来源：JavaGuide 收录题型。

多选3. 关于 redo log、undo log、binlog，正确的有（  ）

A. redo log 是物理日志，崩溃恢复靠它重放，保证持久性
B. undo log 既用于回滚保证原子性，也支撑 MVCC 版本链
C. binlog 属于 Server 层，用于主从复制与数据恢复
D. binlog 是 InnoDB 引擎层的物理日志
答案 ABC。三句话定位：redo 物理+引擎层+崩溃恢复；undo 逻辑+回滚/MVCC；binlog Server 层+主从复制。D 错——binlog 不属于 InnoDB 引擎，且是逻辑日志。来源：面试高频改编。

单选4. 表 t 主键 id 现有值 1、5、10、20。RR 下事务 A 执行 select * from t where id = 8 for update（id=8 不存在），随后事务 B 尝试 insert id=9 的行，结果是（  ）

A. 立即成功，间隙锁只锁已存在的记录
B. 被阻塞，因为 A 的间隙锁锁住了 (5,10) 这个开区间，禁止插入
C. 被阻塞，因为 A 锁了整张表
D. 立即成功，for update 是快照读不加锁
答案 B。id=8 不存在时加的是 (5,10) 的间隙锁（不是记录锁），任何落入该间隙的插入都会被阻塞；这正是 RR 下当前读防幻读的手段。D 错——for update 是当前读，要加锁。来源：面试高频改编。

单选5. 关系模式 R(学号, 姓名, 系名, 系主任)，函数依赖：学号→姓名，学号→系名，系名→系主任。R 最高满足（  ）

A. 2NF
B. 3NF
C. BCNF
D. 1NF
答案 A。姓名、系名都完全依赖候选键"学号"，无部分依赖 → 满足 2NF；但存在传递依赖 学号→系名→系主任 → 不满足 3NF。拆成学生表 + 系表即到 3NF。来源：牛客经典题。

面试口述6. 讲讲 MVCC 是怎么实现可重复读的。

参考回答先说三件套：每行记录有隐藏列 trx_id 和 roll_ptr；每次更新把旧版本写进 undo log，用 roll_ptr 串成版本链；查询时生成 ReadView，含 m_ids（活跃事务列表）、min_trx_id、max_trx_id、creator_trx_id。可见性判断：trx_id 是自己、或小于 min（视图前已提交）就可见；大于等于 max 或还在活跃列表里就不可见，顺 roll_ptr 找旧版本，直到找到可见的。关键一句：RR 只在第一次快照读时生成 ReadView 并全程复用，所以别人后来提交的修改全程不可见，这就是可重复读；RC 是每次快照读都新建 ReadView，所以能读到最新提交。加分点：幻读只是部分解决——快照读靠 MVCC、当前读靠间隙锁；普通 select 是快照读，update/delete/for update 是当前读。来源：面试高频改编。

四、易错点小结

① 一致性是目的，别答成"靠 undo log 保证一致性"；② 不可重复读 vs 幻读：update 改值 vs insert 多行，答题先报侧重；③ 默认级别是 InnoDB 的 RR，别答成 SQL 标准或 RC；④ "RR 彻底解决幻读"是错的——快照读与当前读混用仍有窗口，准确说法是部分解决；⑤ 间隙锁只锁间隙防插入，不锁已存在的记录；id=8 不存在加的就是 (5,10) 间隙锁；⑥ binlog 在 Server 层、redo/undo 在引擎层；主从复制靠 binlog 不是 redo log。
