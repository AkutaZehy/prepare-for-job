Redis 数据类型与持久化

适用岗位：测开(Java)、通用软开、后端 ｜ 形态：类型编码 + 持久化对比 + 架构演进 ｜ 更新：2026-09-30
要点速记：五大类型各配一套底层编码与场景（String 缓存计数 / List 队列 / Hash 对象属性 / Set 去重交集 / ZSet 排行榜，ZSet = skiplist + dict 双结构）；持久化 RDB 快照恢复快但会丢、AOF 追加命令丢得少但文件大（重写压缩、4.0 起混合持久化）；过期删除 = 惰性 + 定期采样；内存淘汰默认 noeviction 报错；快 = 纯内存 + 单线程无锁 + IO 多路复用，6.0 起网络 IO 多线程、命令执行仍单线程；架构三级：主从复制 → 哨兵 → Cluster（16384 slot 分片）。

一、知识点梳理

五大类型：底层编码 + 典型场景 + 常用命令（一张表背完）：

类型底层编码典型场景常用命令
StringSDS 简单动态字符串（O(1) 拿长度、空间预分配、二进制安全）缓存对象（JSON 串）、计数器、分布式锁SET / GET / INCR / SETNX
Listquicklist（3.2 起默认；节点内 7.0 起由 listpack 取代 ziplist）简单消息队列（lpush+rpop）、最新动态列表LPUSH / RPOP / LRANGE
Hash元素少且短用 listpack（7.0 前 ziplist），超阈值转 hashtable对象属性分组存、购物车（field=商品，value=数量）HSET / HGETALL / HINCRBY
Set全为整数用 intset，否则 hashtable去重（点赞/签到）、共同好友（交集）、抽奖SADD / SISMEMBER / SINTER / SRANDMEMBER
ZSet元素少用 listpack，多则 skiplist + dict 双结构：跳表管排序与范围，dict 管 O(1) 按成员查分排行榜、延迟队列（score=执行时间）ZADD / ZRANGE / ZREVRANGE / ZSCORE

跳表 vs 红黑树（ZSet 为什么选跳表，一句话版）：跳表底层是有序链表，范围查询沿链表顺序走即可、定位 O(logn)，而红黑树范围查询要中序遍历上下来回爬；跳表实现简单（无旋转调色），还天然支持按排名 rank 定位，编码维护成本低——所以 ZSet 用跳表不用红黑树。

过期删除策略：惰性删除（key 被访问时才检查，过期即删——冷 key 可能长期占内存）+ 定期删除（默认每 100ms 随机抽样一批设置了过期时间的 key，删掉其中过期的，限制时长防阻塞主线程）两者组合使用，互补短板。

内存淘汰 8 种（maxmemory-policy，内存满触发）：

策略范围规则
noeviction（默认）—不淘汰，内存满后写命令直接报错（读不受影响）
allkeys-lru / volatile-lru全部 key / 仅设了过期时间的 key淘汰最久未使用的（近似 LRU：采样而非全局精确链表）
allkeys-lfu / volatile-lfu同上两个范围淘汰访问频率最低的（4.0 起；计数+随时间衰减）
allkeys-random / volatile-random同上两个范围随机淘汰
volatile-ttl仅设了过期时间的 key淘汰剩余存活时间最短的

LRU vs LFU 一句话：LRU 看"最近有没有用"（偶发批量扫描会污染）；LFU 看"用得多不多"（按频率计数并衰减），偶发扫描场景 LFU 更稳。

持久化：RDB vs AOF 大对比：

维度RDB（快照）AOF（追加日志）
原理把某时刻全量数据以二进制落盘；save 阻塞主线程（别用），bgsave fork 子进程 + 写时复制 COW（主进程继续改，子进程按 fork 瞬间的快照写）追加记录每条写命令；写后日志（先执行命令再记日志，防记录错误命令、不阻塞当前写，代价是宕机可能丢最后一条）
刷盘三档按 save 配置定时间隔appendfsync：always 每条命令都 fsync（最安全最慢）/ everysec（默认，最多丢约 1 秒）/ no 交给操作系统（最快最不安全）
体积与恢复二进制紧凑、恢复快文本命令文件大、恢复慢；AOF 重写 bgrewriteaof：fork 子进程按当前内存数据反推最小命令集压缩体积，重写期间新命令进"AOF 重写缓冲区"最后补上
数据安全两次快照之间的宕机会丢一段everysec 下最多丢约 1 秒

4.0 起混合持久化（aof-use-rdb-preamble）：AOF 重写后的文件 = RDB 全量二进制做头 + 之后增量 AOF 追加做尾——恢复速度向 RDB 看齐、丢数据向 AOF 看齐，4.0+ 推荐。

Redis 为什么快：①纯内存操作；②命令执行单线程——无锁竞争、无线程上下文切换；③IO 多路复用（epoll），单线程就能管理大量连接；④数据结构高效（SDS、跳表、listpack 等都是为内存与速度定制）。版本注：Redis 6.0 起网络 IO（读取、解析、回写）改多线程，但命令执行仍是单线程——面试别说成"6.0 后整体多线程"。

高可用三级架构（各一句）：主从复制——主写从读、读写分离，首次全量 RDB 同步 + 之后异步命令传播（异步就有丢失窗口）；哨兵 Sentinel——监控主库健康，主观下线→多数派确认客观下线，自动选举新主并故障转移、通知客户端，哨兵自身至少 3 节点防误判；Cluster 集群——数据按 key 的 CRC16 值 % 16384 定位 slot 分片到各主节点（各管一部分槽），内置主从与故障转移。加分点：slot 定 16384 是心跳包体积的权衡（65536 的心跳头太大，8K 槽又不够分片规模）。

三、示例题目（点击选项即时判分）

单选1. 要实现游戏排行榜：按积分排序取前 100 名、随时更新某玩家积分、并要求 O(1) 查询某玩家的积分。最合适的 Redis 数据类型是（  ）

A. List，LRANGE 分页取名次
B. Hash，field 存玩家名 value 存积分
C. ZSet，score 存积分，skiplist + dict 双结构同时满足排序与点查
D. Set，天然去重存玩家集合
答案 C。ZSet 的双结构正好对上两个需求：跳表管 ZREVRANGE 排序取前 N，dict 管 ZSCORE 的 O(1) 点查。Hash 没法按值排序；List 排序要全量扫。来源：牛客经典题。

多选2. 关于 RDB 与 AOF，正确的有（  ）

A. bgsave 靠 fork 子进程 + 写时复制实现，基本不阻塞主线程（fork 瞬间除外）
B. appendfsync everysec 是默认配置，宕机最多丢约 1 秒的数据
C. AOF 重写按当前内存数据反推最小命令集，能大幅压缩文件体积
D. RDB 文件的恢复速度比 AOF 慢
答案 ABC。RDB 是二进制全量快照，直接载入内存即可，恢复比 AOF 快，D 反了。AOF 恢复要逐条重放命令，所以才有了重写压缩和 4.0 的"RDB 头 + AOF 尾"混合格式。来源：JavaGuide 收录题型。

单选3. 金融类业务要求 Redis 宕机时几乎不丢数据，AOF 的 appendfsync 应配置为（  ）

A. no，交给操作系统调度
B. everysec，每秒刷一次
C. always，每条命令都 fsync
D. 关掉 AOF 只用 RDB
答案 C。always 每条命令都落盘，性能最差但最安全；everysec 默认，最多丢约 1 秒；no 交给 OS，窗口不可控。只配 RDB 会丢两次快照之间的全部数据。来源：面试高频改编。

单选4. Redis 纯作缓存使用（key 未统一设置过期时间），内存已打满但仍需继续写入，希望淘汰任意 key 中"最久未被使用"的，应配置（  ）

A. noeviction
B. volatile-lru
C. allkeys-lru
D. volatile-ttl
答案 C。volatile 系只在设置了过期时间的 key 里淘汰——纯缓存未必都设 TTL，样本可能为空导致写入报错；全量范围 + LRU 语义 = allkeys-lru。默认策略是 noeviction（只报错不淘汰）。来源：面试高频改编。

面试口述5. ZSet 底层为什么用跳表而不是红黑树？两句话说清。

参考回答第一，范围查询：跳表的底层是有序链表，找到起点后沿链表顺序走就是ZRANGE/ZREVRANGE，天然高效；红黑树做范围查询要中序遍历，指针上下来回爬。第二，工程实现：跳表靠随机层数维持平衡，没有旋转和变色，实现和调试都简单，还容易支持按排名 rank 查询；配合 dict 就能做到按成员 O(1) 查分数。加分点：说清 ZSet 是 skiplist + dict 双结构，以及元素少时先用 listpack 省内存。来源：面试高频改编。

四、易错点小结

① volatile 系淘汰只作用于设了过期时间的 key——纯缓存要选 allkeys 系；Redis 的 LRU 是采样近似 LRU，不是全局精确链表；② save 阻塞主线程，生产用 bgsave（fork + COW）；③ AOF 是写后日志（先命令后日志），与 redo log 的先日志后数据（WAL）方向相反，别背串；④ 6.0 的多线程只管网络 IO，命令执行永远单线程；⑤ 版本锚点：quicklist 是 3.2 起 List 默认；listpack 替换 ziplist 是 7.0；LFU 与混合持久化是 4.0；⑥ 惰性 + 定期是"过期删除"，内存满触发的是"淘汰策略"——两套机制别混。
