要点速记：MyBatis——#{} 预编译防注入，${} 拼接只给表名列名；MQ——削峰填谷/解耦/异步，消息丢失三环节（生产者/Broker/消费者）各有一策，重复消费靠业务幂等；Linux——查端口 lsof -i:端口、追日志 tail -f、CPU 飙高 top → top -Hp → printf 转十六进制 → jstack；Git——没 push 用 reset、已 push 用 revert，公共分支禁止 rebase。

一、知识点梳理

1. MyBatis：#{} vs ${}、resultMap、缓存

写法底层行为用法与风险
#{}预编译占位符，编译成 ?，由 PreparedStatement 按类型安全代入传"值"一律用它，天然防 SQL 注入
${}字符串拼接，参数原样嵌进 SQL只用于表名、列名、ORDER BY 列名等无法参数化的位置，且必须白名单校验，否则就是注入入口
SQL 
SELECT * FROM user WHERE name = #{name}    -- 预编译：WHERE name = ?
SELECT * FROM user ORDER BY ${orderCol}    -- 拼接：ORDER BY age（仅列名场景，白名单校验）
  • resultMap：列名与实体属性名不一致、或一对一/一对多关联映射时用；列名与属性名一致（或开启驼峰映射）用 resultType 就够。
  • 缓存一句话：一级缓存 SqlSession 级、默认开启；二级缓存 namespace 级、手动开启，跨 SqlSession 共享——多表更新容易脏读，实践中常让位给 Redis。

2. 消息队列 MQ：三大价值、消息丢失、重复消费

  • 三大价值：削峰填谷（流量洪峰先入队，消费端按自己的节奏处理）、系统解耦（生产者与消费者互不感知）、异步提速（主流程不等非核心链路）。
丢失环节典型原因对策
生产者 → Broker网络失败、发送后不确认confirm 确认机制 / 事务消息、失败重试、本地消息表
Broker 自身消息还没落盘就宕机持久化 + 集群多副本（Kafka 多副本 + acks=all；RocketMQ 同步刷盘、主从）
Broker → 消费者先提交 offset 再处理，处理时崩溃；处理失败业务处理成功后再手动 ack；失败进重试队列与死信队列
  • 重复消费：MQ 只承诺 at-least-once（至少一次），重试必然带来重复——幂等由业务保证：数据库唯一键、去重表、状态机校验流转、Redis setnx 去重。

3. Linux 高频命令

命令用途
top实时进程 CPU/内存；P 按 CPU 排序、M 按内存排序
ps -ef | grep xxx查指定进程（快照）
kill -9 PID强制杀进程（SIGKILL，进程无法拦截）
grep -r "关键字" ./递归搜索文件内容
awk '{print $1}'按列取字段（默认按空格分列）
netstat -tlnp看本机监听端口及对应进程
lsof -i:8080查 8080 端口被哪个进程占用
df -h磁盘各分区容量
du -sh 目录某目录总占用大小
free -h内存使用（-h 人类可读单位）
tail -f app.log实时追加查看日志
nohup java -jar app.jar &后台运行且退出终端不挂断
Shell 
# 线上 CPU 飙高排查四步（口述题必备，背熟）
top                              # ① 找到最耗 CPU 的 Java 进程，记下 PID
top -Hp 12345                    # ② 看该进程内最耗 CPU 的线程，记下线程号 TID
printf '%x\n' 12378              # ③ 十进制线程号转十六进制，得 305a
jstack 12345 | grep -A 30 305a   # ④ 看该线程栈卡在哪段代码

4. Git 高频

  • merge vs rebase：merge 保留分叉历史、多一条合并提交；rebase 把本分支提交"搬到"目标分支之后，历史线性好看。已 push 的公共分支禁止 rebase——改写历史坑队友。
  • reset 三档：--soft 只回退 HEAD，改动留在暂存区（想重新组织提交）；--mixed（默认）回退 HEAD + 暂存区，改动留在工作区；--hard 三处全回退、工作区改动一并丢弃，慎用。
  • stash：改到一半要切分支——git stash 暂存，回来 git stash pop 恢复。
  • 冲突解决流程：merge/rebase 报冲突 → 打开文件处理冲突标记块 → git add → merge 就 git commit、rebase 就 git rebase --continue。
  • 撤销已 push 的 commit：用 git revert 生成一条反向提交，安全、可正常推送；公共分支不要 reset --hard + force push。
Git 
git stash                # 改动暂存
git stash pop            # 恢复暂存
git reset --soft HEAD^   # 撤销上次 commit，改动回暂存区
git revert abc1234       # 反向提交，撤销已 push 的 commit

# 冲突标记块（手动处理后 add、继续合并/变基）
<<<<<<< HEAD
当前分支的改动
=======
要合入分支的改动
>>>>>>> feature/x

三、示例题目（点击选项即时判分）

单选1. MyBatis 中关于 #{} 与 ${}，说法正确的是（  ）

A. #{} 走预编译（PreparedStatement 占位符）防 SQL 注入；${} 是字符串拼接，只用于表名/列名等无法参数化的位置并做白名单校验
B. 两者都会走 PreparedStatement 预编译，只是写法不同
C. ${} 更安全，动态 SQL 应全部使用 ${}
D. #{} 用于传表名最方便
答案 A。#{} 编译成 ? 由驱动按类型安全代入；${} 把参数原样拼进 SQL，传 "or 1=1 --" 就是注入入口。表名/列名场景用 ${} 拼接后必须白名单校验。来源：牛客经典题。

多选2. 关于 MQ 消息丢失与重复消费，正确的有（  ）

A. 生产者开启 confirm 确认 / 事务消息，发送失败重试，防"没到 Broker 就丢"
B. Broker 侧持久化 + 多副本（如 Kafka acks=all），防宕机丢消息
C. 消费者业务处理成功后再手动 ack，失败进入重试队列与死信队列
D. 开了持久化与手动 ack 后，MQ 保证恰好一次投递，业务无需做幂等
答案 ABC。D 错——MQ 只承诺 at-least-once，重试必然带来重复，幂等必须业务自己保证：唯一键、去重表、状态机流转、Redis setnx。来源：面试高频改编。

单选3. 想知道 8080 端口被哪个进程占用，最直接的命令是（  ）

A. lsof -i:8080（或 netstat -tlnp | grep 8080）
B. df -h | grep 8080
C. ps -ef | grep 8080
D. free -h | grep 8080
答案 A。lsof -i:8080 直接列出占用该端口的进程；netstat -tlnp 列出监听端口再 grep 也行。C 看似可行实则碰运气——ps 过滤的是进程名与启动参数，端口号不一定出现在参数里。df 是磁盘容量、free 是内存。来源：面试高频改编。

单选4. 下列哪种场景适合用 rebase（  ）

A. 在个人功能分支上，把本地提交变基到最新 main 之上，保持线性历史后再合入
B. 在多人共用的公共分支上，rebase 改写已 push 的提交历史
C. 想撤销一次已经 push 的 commit
D. 想把工作区没提交的改动临时存起来，稍后恢复
答案 A。rebase 改写历史，只能用在未共享的个人分支；B 是坑队友的反面操作；C 对应 git revert；D 对应 git stash。来源：JavaGuide 收录题型。

面试口述5. 线上 Java 服务 CPU 飙到 100%，口述完整排查流程。

参考回答按固定四步：① top 找到最耗 CPU 的 Java 进程，记下进程号；② top -Hp 进程号，看该进程里最耗 CPU 的线程，记下线程号；③ printf '%x\n' 线程号，把十进制线程号转成十六进制；④ jstack 进程号 | grep -A 30 十六进制值，拿到该线程的栈，看它卡在哪段代码——常见元凶：死循环、频繁正则回溯、大量 GC（可用 jstat -gcutil 确认是不是 GC 线程在烧 CPU）。定位到栈就回代码修复。加分点：隔几秒抓两次栈对比、arthas 的 dashboard/thread 命令一键定位。来源：牛客经典题。

四、易错点小结

① ${} 只留给表名列名并白名单校验，传值一律 #{}；② 消息可靠性 = 生产者 confirm + Broker 持久化多副本 + 消费者手动 ack 三段各管一段，幂等兜底靠业务（唯一键/去重表/状态机）；③ 查端口 lsof -i:端口、追日志 tail -f、杀进程 kill -9 是现场操作底线三连；④ Git 撤销：没 push 用 reset（分清三档），已 push 用 revert；公共分支永远不 rebase、不 force push。
