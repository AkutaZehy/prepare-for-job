SpringBoot 核心：IoC、Bean 与自动装配

适用岗位：测开(Java)、通用软开（Spring 八股必经之路） ｜ 形态：原理 + 流程 + 版本注记 ｜ 更新：2026-09-30
要点速记：IoC = 对象的创建与依赖交给容器，DI 是实现手段；生命周期口诀——实例化→属性填充→初始化（@PostConstruct → afterPropertiesSet → init-method）→BeanPostProcessor 后置里生成 AOP 代理→销毁；三级缓存解决 setter 循环依赖（构造器与 prototype 无解，三级为的是 AOP 代理一致性）；@Autowired 按类型、@Resource 按名称；自动装配必背：@SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan，靠 AutoConfigurationImportSelector 读 imports 文件 + 条件注解按需生效——约定大于配置。

一、知识点梳理

IoC 与 DI：控制反转——对象的创建、依赖装配、生命周期管理从程序员手里交给 IoC 容器，代码从"主动 new"变成"被动注入"。依赖注入（DI）是实现 IoC 的手段：构造器注入、setter 注入、字段注入。收益：解耦（面向接口）、可替换、好测试（mock 直接注入）。

BeanFactory vs ApplicationContext：BeanFactory 是最底层容器，懒加载（getBean 时才实例化单例）；ApplicationContext 是它的超集，启动时就预实例化全部单例，外加事件发布、国际化、资源加载——实际开发用的都是 ApplicationContext。

Bean 生命周期（简版必背）：

① 实例化（构造器/工厂方法，半成品）
② 属性填充（@Autowired / @Resource 依赖注入）+ Aware 回调（BeanNameAware / ApplicationContextAware…）
③ BeanPostProcessor 前置处理
④ 初始化：@PostConstruct → InitializingBean#afterPropertiesSet → init-method（固定顺序）
⑤ BeanPostProcessor 后置处理 ← AOP 代理对象在这里生成并替换原对象
⑥ 使用 …… ⑦ 销毁：@PreDestroy → DisposableBean#destroy → destroy-method

记忆锚点：初始化前后各夹一个 BeanPostProcessor；代理在后置处理里出现——这句话是理解循环依赖与 AOP 关系的钥匙（代理细节见同目录 AOP动态代理与事务失效）。

三级缓存解决 setter / 字段注入的循环依赖：

缓存存什么
一级 singletonObjects完全就绪的成品单例
二级 earlySingletonObjects早期引用（已实例化、还没填充属性）
三级 singletonFactoriesObjectFactory 工厂——被循环依赖时才调用，按需产出原对象或提前生成的代理

流程：A 实例化后把自己的工厂放三级 → 填充属性发现要 B → 创建 B → B 填充属性要 A → 从三级缓存取出 A 的早期引用（必要时此处产出代理）放进二级、删三级 → B 拿着它完成 → A 继续完成。一句话：靠"实例化后、初始化前"这个半成品窗口提前暴露引用。

为什么三级不是二级：AOP 代理一致性——代理本该在初始化后的后置处理里生成；二级方案就得"所有 bean 一实例化就立刻生成代理"，破坏生命周期设计。三级用工厂延迟决定：没人循环依赖我就走正常流程，有人依赖我才提前出代理，并保证 A 全容器只代理一次。

无解场景：构造器注入循环依赖（互相在实例化阶段就要对方，早期引用还没机会进缓存，直接 BeanCurrentlyInCreationException）；prototype 作用域（不走单例缓存）。版本注：SpringBoot 2.6 起默认禁止循环依赖，需 spring.main.allow-circular-references=true——更推荐靠设计拆掉循环。

五种作用域：singleton（默认，容器级一个——注意是"容器级"不是 JVM 级单例）、prototype（每次 getBean 新建）、request（每个 HTTP 请求）、session（每个会话）、websocket（每个 WebSocket 连接）；后三个用于 web 环境。

@Autowired vs @Resource：

维度@Autowired@Resource
来源Spring 提供JDK 标准（JSR-250）
匹配规则默认 byType；同类型多个候选时按属性名再找，仍歧义则报错——配 @Primary 指首选、@Qualifier("名") 指定；required=false 允许没有默认 byName（不指定 name 用字段名），找不到名字再回退 byType

记忆：A(utowired)=按类型自动配；R(esource)=按资源名找。

组件注册四途径：①@Component 及派生（@Service/@Repository/@Controller/@Configuration），配合 @ComponentScan 扫描（Boot 主类默认扫主类所在包及子包）；②@Bean——配置类方法上注册，第三方类没法改源码加注解时用；③@Import——导入配置类/普通类/ImportSelector 实现批量注册；④FactoryBean——工厂 Bean，getBean 拿到的是 getObject 产物、加 & 前缀拿工厂本身（MyBatis 的 SqlSessionFactoryBean 就是）。

SpringBoot 自动装配原理（必背，面试开场白）：

  • @SpringBootApplication = @SpringBootConfiguration（即 @Configuration）+ @EnableAutoConfiguration + @ComponentScan。
  • @EnableAutoConfiguration 内部 @Import(AutoConfigurationImportSelector)：启动时读取所有 jar 包的 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（SpringBoot 2.7 起的文件位置；2.7 前读 spring.factories 中 EnableAutoConfiguration 键），拿到全部候选自动配置类。
  • 候选类再被条件注解逐个过滤：@ConditionalOnClass（类路径存在该类才生效）、@ConditionalOnMissingBean（用户没自定义才给默认）等——留存的配置类批量注册 Bean。
  • 一句话："约定大于配置"= 把你以前手写的配置类按条件自动化；starter = 依赖聚合（一组坐标一次引入）+ 自动配置，开箱即用。
Java 
// 自动装配的最小模型：一个"候选配置类"靠条件注解决定是否生效
@Configuration
@ConditionalOnClass(DataSource.class)      // 类路径上有 DataSource 才生效
public class DataSourceAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean              // 用户自己没配 DataSource 才给默认的
    public DataSource defaultDataSource() {
        return new HikariDataSource();
    }
}
// 这就是"引了 starter 就能用、想覆盖就自己声明同类型 Bean"的全部原理

二、考点说明

笔试选择面试必问

  • 笔试：生命周期顺序（三兄弟 @PostConstruct → afterPropertiesSet → init-method）、作用域、@Autowired vs @Resource 匹配规则、循环依赖哪些无解。
  • 面试："SpringBoot 自动装配原理"（按上面四步背）、"为什么需要三级缓存而不是二级"、"构造器注入为什么解决不了循环依赖"、"BeanFactory 和 ApplicationContext 区别"。
  • 追问链：生命周期 → BeanPostProcessor → AOP 代理生成时机 → 三级缓存 → 2.6 默认禁止循环依赖，一环扣一环。

三、示例题目（点击选项即时判分）

单选1. 同一个 Bean 中：@PostConstruct（甲）、afterPropertiesSet（乙）、init-method（丙）、BeanPostProcessor 后置方法（丁），执行顺序正确的是（  ）

A. 甲 → 乙 → 丙 → 丁
B. 乙 → 甲 → 丙 → 丁
C. 丁 → 甲 → 乙 → 丙
D. 甲 → 丙 → 乙 → 丁
答案 A。初始化三兄弟固定顺序 @PostConstruct → afterPropertiesSet → init-method，而 BeanPostProcessor 后置在三者全部结束之后——AOP 代理正是这时生成的。来源：牛客经典题。

多选2. 关于 Spring 三级缓存解决循环依赖，正确的有（  ）

A. 一级缓存 singletonObjects 存放完全就绪的成品单例
B. 二级缓存 earlySingletonObjects 存放"已实例化但未填充属性"的早期引用
C. 三级缓存放 ObjectFactory，被依赖时才调用，用于按需产出早期引用（可能是代理）
D. 三级缓存主要用于解决构造器注入的循环依赖
答案 ABC。三级缓存只救 setter/字段注入的单例循环依赖；构造器注入在实例化阶段就互相要对方，早期引用还没机会暴露，D 错。三级为的是 AOP 代理一致性：工厂延迟决定给原对象还是提前代理，且全容器只代理一次。来源：JavaGuide 收录题型。

单选3. 关于 @Resource 注解的注入规则，正确的是（  ）

A. 只按类型匹配，多个候选时报错
B. 默认先按名称匹配，找不到名称再回退按类型
C. 只按名称匹配，找不到直接报错，永不回退
D. 它是 Spring 提供的注解，与 JDK 无关
答案 B。@Resource（JSR-250，JDK 标准）默认 byName（未指定 name 时用字段名），找不到再回退 byType；显式写了 name 属性才"找不到就报错"。A 说的是 @Autowired。来源：牛客经典题。

单选4. A、B 两个类通过构造器互相注入，Spring 启动抛 BeanCurrentlyInCreationException。根本原因是（  ）

A. 三级缓存的容量太小存不下两个 bean
B. 构造器注入的优先级低于字段注入
C. 构造器注入在实例化阶段就要对方，而"早期引用"要等实例化完成后才可能暴露进缓存——A 还没 new 出来就谈不上提前暴露
D. prototype 作用域不支持依赖注入
答案 C。三级缓存救循环依赖的前提是"实例化完成、属性还没填"这个半成品窗口；构造器注入把依赖提前到了实例化内部，窗口不存在。setter/字段注入才有救。来源：面试高频改编。

面试口述5. 背一遍 SpringBoot 自动装配原理。

参考回答入口：@SpringBootApplication 是三个注解的组合——@SpringBootConfiguration（本质 @Configuration）、@EnableAutoConfiguration、@ComponentScan（扫主类所在包及子包）。核心在 @EnableAutoConfiguration：它 @Import 了 AutoConfigurationImportSelector，启动时读取所有 jar 里 META-INF/spring/…AutoConfiguration.imports 文件（2.7 起的路径，2.7 前是 spring.factories 的 EnableAutoConfiguration 键），拿到全部候选自动配置类；再用 @ConditionalOnClass、@ConditionalOnMissingBean 等条件注解逐个过滤——类路径有才生效、用户没自己配才给默认——留存的配置类批量注册 Bean。一句话总结：约定大于配置；starter = 依赖聚合 + 自动配置。加分点：主动提 2.7 前后文件位置变化、@ConditionalOnMissingBean 保证用户覆盖优先。来源：面试高频改编。

四、易错点小结

① 初始化三兄弟顺序别乱：@PostConstruct → afterPropertiesSet → init-method；AOP 代理在 BeanPostProcessor 后置生成；② 三级缓存只救"单例 + setter/字段注入"，构造器与 prototype 无解——答题先说前提；③ SpringBoot 2.6 起默认禁止循环依赖，别再说"循环依赖随便用"；④ @Autowired byType（多候选配 @Primary/@Qualifier），@Resource byName 失败回退 byType；⑤ 自动装配文件位置版本分界：2.7 前 spring.factories、2.7 起 META-INF/spring/…imports；⑥ singleton 是容器级单例，同一 JVM 起两个容器就有两个实例，与 JVM 单例模式不是一回事。
