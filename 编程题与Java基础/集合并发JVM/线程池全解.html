线程池全解

适用岗位：测开(Java)、通用软开（八股与笔试双高频） ｜ 形态：参数 + 流程 + 模板代码 ｜ 更新：2026-09-30
要点速记：七大参数 core / max / keepAlive+unit / workQueue / threadFactory / handler；执行流程（易错重灾区）：核心线程 → 任务入队 → 队列满了才开非核心线程 → 达到 maximum 就拒绝（不是先开满线程再入队！）；拒绝四策略 AbortPolicy 默认抛 RejectedExecutionException；Executors 两大坑：Fixed 无界队列 OOM、Cached 线程数 Integer.MAX_VALUE；线程数经验：CPU 密集 N+1、IO 密集 N×(1+等待/计算)；shutdown 跑完已提交任务 vs shutdownNow 中断；submit 的异常吞进 Future。

一、知识点梳理

为什么用线程池：①线程创建/销毁有系统调用开销，池化复用降低开销；②控制并发线程上限，防止资源被无限线程拖垮（限流）；③统一管理：排队、命名、监控、拒绝策略，任务提交方与执行方解耦。

七大参数（ThreadPoolExecutor 构造器顺序）：

参数含义要点
corePoolSize核心线程数默认常驻不回收（allowCoreThreadTimeOut(true) 可让核心也超时回收）
maximumPoolSize最大线程数核心 + 非核心的总上限
keepAliveTime + unit空闲存活时间非核心线程空闲超过它就被回收
workQueue任务队列提交了但还没执行的任务；有界/无界直接决定池的行为
threadFactory线程工厂起线程名、设优先级/守护态——排障全靠名字
handler拒绝策略队列满且线程也满时触发

执行流程（背到条件反射）：提交任务后——①运行线程数 < corePoolSize？新建核心线程执行；②否则任务先入队（队列没满就不开新线程！）；③队列也满了？才开非核心线程，直到 maximumPoolSize；④线程达到 maximum 且队列满？触发拒绝策略。

提交任务 execute(task)
    │
    ├─ 线程数 < corePoolSize ？ ── 是 ──→ 新建核心线程执行
    │        ↓ 否
    ├─ workQueue 未满 ？       ── 是 ──→ 任务入队等待（不开新线程！）
    │        ↓ 否
    ├─ 线程数 < maximumPoolSize？── 是 ──→ 新建非核心线程执行
    │        ↓ 否
    └─ 触发拒绝策略 handler.rejectedExecution(...)

四种拒绝策略：

策略行为备注
AbortPolicy直接抛 RejectedExecutionException默认策略，让提交方立刻感知过载
CallerRunsPolicy由提交任务的线程（调用者）自己执行天然反压：提交被拖慢，任务不丢
DiscardPolicy静默丢弃新任务无任何感知，慎用
DiscardOldestPolicy丢弃队首最老任务，再重试提交当前任务老任务让位新任务

为什么阿里规约禁止直接用 Executors：newFixedThreadPool / newSingleThreadExecutor 用默认容量的 LinkedBlockingQueue（容量 Integer.MAX_VALUE，无界）——任务无限堆积 OOM；newCachedThreadPool / newScheduledThreadPool 的 maximumPoolSize 是 Integer.MAX_VALUE——线程无限膨胀 OOM。规约要求手动 new ThreadPoolExecutor，显式给有界队列 + 命名线程工厂 + 明确拒绝策略。

线程数经验公式（经验值非定理，最终以压测为准）：CPU 密集型 = 核数 + 1（+1 防偶发缺页等暂停浪费一核）；IO 密集型 = 核数 × (1 + 等待时间/计算时间)——等待占比越高，线程数可以越多。

shutdown vs shutdownNow：shutdown()——不再接收新任务，已提交（含队列中）的任务全部跑完后关闭；shutdownNow()——不再接收新任务，并尝试中断正在执行的线程，返回队列中未执行的任务列表。

submit vs execute：execute(Runnable) 无返回值，任务抛的异常直接走线程的未捕获异常处理（默认打印堆栈）；submit(...) 返回 Future，异常被捕获存进 Future，不调用 get() 就完全看不到——"任务静默失败"的经典来源。

常用排队策略：ArrayBlockingQueue——有界，必须指定容量，配合拒绝策略形成反压；LinkedBlockingQueue——可有界可无界（默认容量 Integer.MAX_VALUE ≈ 无界，风险所在）；SynchronousQueue——不存任务、直接交接，CachedThreadPool 的选择，每个提交立刻需要一个空闲线程接住。

动态调参一句：ThreadPoolExecutor 提供 setCorePoolSize / setMaximumPoolSize 等运行时修改接口，是配置中心热调线程池的基础。

Java 
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        4,                                  // corePoolSize：核心线程数
        8,                                  // maximumPoolSize：最大线程数
        60L, TimeUnit.SECONDS,              // keepAliveTime+unit：非核心空闲 60s 回收
        new ArrayBlockingQueue<>(100),      // workQueue：有界队列，容量 100
        r -> {                              // threadFactory：命名线程工厂（排障必备）
            Thread t = new Thread(r, "biz-pool-" + SEQ.getAndIncrement());
            t.setDaemon(false);
            return t;
        },
        new ThreadPoolExecutor.CallerRunsPolicy()   // handler：池满由提交线程自己跑（反压）
);
static final AtomicInteger SEQ = new AtomicInteger(1);

try {
    pool.execute(() -> System.out.println("无返回值任务"));  // execute：异常直接打印堆栈
    Future<Integer> f = pool.submit(() -> 42);               // submit：返回 Future
    System.out.println(f.get(1, TimeUnit.SECONDS));          // 任务异常在 get() 时才抛出
} catch (Exception e) {
    e.printStackTrace();
} finally {
    pool.shutdown();                       // 温和关闭：不再收新任务，已提交的跑完
}
Python 
# 对照：concurrent.futures.ThreadPoolExecutor 只有 max_workers 一个旋钮
from concurrent.futures import ThreadPoolExecutor
with ThreadPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(lambda x: x * x, range(10)))

三、示例题目（点击选项即时判分）

计算1. 线程池参数：核心线程 3、队列容量 10、最大线程 6。假设前 13 个任务都长时间未执行完，问提交第 14 个任务时发生什么？提交第 20 个呢？写出过程。

先自己算，再展开对答案容量账本：核心 3 + 队列 10 = 前 13 个任务"无压力"——第 1~3 个开满核心线程，第 4~13 个依次入队（第 13 个把队列装满）。第 14 个：队列已满 → 开第 1 个非核心线程（池中第 4 个线程）执行；第 15、16 个各再开一个非核心线程，到第 16 个时线程达 maximum=6。第 17 个起（含第 20 个）：核心满 + 队列满 + 线程满 → 触发拒绝策略，默认 AbortPolicy 抛 RejectedExecutionException。记忆点：池的总承载力 = 核心 + 队列 + 非核心 = 3+10+3 = 16 个。来源：牛客经典题。

多选2. 关于四种拒绝策略，正确的有（  ）

A. AbortPolicy 是默认策略，直接抛 RejectedExecutionException
B. CallerRunsPolicy 由提交任务的线程自己执行，能起到反压降速作用
C. DiscardOldestPolicy 丢弃刚刚提交的最新任务
D. DiscardPolicy 静默丢弃新提交的任务，不抛异常
答案 ABD。C 反了——DiscardOldestPolicy 丢的是队首最老的任务，给新任务腾位。CallerRuns 的反压原理：提交线程亲自执行任务期间，就没法继续提交，整体速度被拖回池的处理能力。来源：牛客经典题。

多选3. 关于 Executors 工厂方法的风险（阿里规约禁用），正确的有（  ）

A. newFixedThreadPool / newSingleThreadExecutor 用默认容量 Integer.MAX_VALUE 的 LinkedBlockingQueue，任务堆积可能 OOM
B. newCachedThreadPool 的 maximumPoolSize 是 Integer.MAX_VALUE，线程可能无限膨胀 OOM
C. newSingleThreadExecutor 使用有界队列，天然安全
D. 只要配置了拒绝策略，就不会发生 OOM
答案 AB。C 错——newSingleThreadExecutor 同样是无界 LinkedBlockingQueue；D 错——拒绝策略只在"队列满且线程满"时触发，无界队列永远不满，拒绝策略形同虚设，OOM 风险照样存在。正解：手动 new ThreadPoolExecutor + 有界队列。来源：JavaGuide 收录题型。

单选4. 线程池核心线程已满、队列未满，此时提交新任务会（  ）

A. 立即创建非核心线程执行
B. 任务入队等待，不开新线程
C. 触发拒绝策略
D. 丢弃队首任务给新任务腾位置
答案 B。执行流程最经典陷阱：非核心线程只在"队列也满了"之后才创建，入队永远优先于扩线程。推论（面试加分）：newFixedThreadPool 的队列无界 → 永远不会满 → 最大线程数形同虚设，永远只有核心线程在干活。来源：面试高频改编。

单选5. 用 submit 提交的任务抛出运行时异常，且代码从不调用返回的 Future.get()，现象是（  ）

A. 异常堆栈打印到控制台/日志
B. 异常被存进 Future，不调用 get() 就无人感知，任务静默失败
C. 异常导致整个线程池关闭
D. 异常触发拒绝策略重跑任务
答案 B。submit 把任务包成 FutureTask，异常被捕获存进去，get() 时才以 ExecutionException 抛出——不 get 就"消失"。execute 提交的任务异常才直接走线程的未捕获异常处理。生产上排查"任务悄悄没跑成"先想到这一条。来源：面试高频改编。

面试口述6. 8 核机器上有两类任务：①纯 CPU 计算；②调用外部 HTTP，单次 200ms 中约 180ms 在等响应。两类任务各自的线程池线程数怎么设？队列怎么选？

参考回答①CPU 密集：核数 + 1 = 9 个上下（公式 N+1），线程再多只会增加上下文切换开销；②IO 密集：N × (1 + 等待/计算) = 8 × (1 + 180/20) = 8 × 10 = 80 作为起点（等待占比 90%，大部分时间线程在睡，可以多放），再压测微调。队列选有界 ArrayBlockingQueue（容量按峰值容忍度定），避免无界堆积 OOM；拒绝策略视业务：不能丢选 CallerRuns，可降级选 Abort + 监控告警；线程工厂必须命名。收尾强调：公式是经验起点，最终以压测为准，CPU 密集也可按"核数±1"微调。来源：面试高频改编。

四、易错点小结

① 顺序口诀：核心 → 队列 → 非核心 → 拒绝；"先入队还是先开线程"答反即丢分；② 无界队列 = 最大线程数与拒绝策略同时失效（队列永远不满）；③ submit 异常进 Future、execute 异常直接抛——排查静默失败的第一反应；④ shutdown 与 shutdownNow 都不接新任务，差别只在是否中断正在执行的线程；⑤ 线程数公式是起点不是终点，压测才是终点。
