JVM 调优与排障工具（OOM/jmap/jstack）

适用岗位：后端/测开面试高频 ｜ 关联页：垃圾回收与收集器、ThreadLocal 与并发工具类 ｜ 更新：2026-09-30
要点速记：线上排障三板斧——CPU 高：top 找进程 → top -Hp 找线程 → 线程号转十六进制 → jstack 里按 nid 定位栈；内存涨/泄漏：jmap -histo 看对象直方图、jmap -dump + MAT 看支配树；GC 频繁：jstat -gcutil 看 GC 占比与频率。OOM 先分清类型再谈方案，-XX:+HeapDumpOnOutOfMemoryError 提前埋好现场。

一、知识点梳理

常见 OOM 类型与归因：

报错关键词区域典型原因
Java heap space堆大对象/集合无限增长、堆设置过小、内存泄漏
GC overhead limit exceeded堆GC 时间占比 > 98% 但回收不到 2%——泄漏的预警信号
Metaspace元空间动态生成类太多（CGLIB 代理、反射、Groovy 脚本），类加载器泄漏
unable to create new native thread线程线程数超系统限制，无界线程池 + 泄漏
Direct buffer memory堆外NIO DirectByteBuffer 超出 -XX:MaxDirectMemorySize

命令行工具全家桶：

命令作用一句话记忆
jps -l列 Java 进程第一步先找到 pid
jstat -gcutil pid 1000 10GC 各区占用/次数/耗时快照看 YGC/FGC 频率与 O 区是否只涨不跌
jmap -histo:live pid对象直方图（触发 Full GC）内存泄漏先看谁最多
jmap -dump:live,format=b,file=a.hprof pid导出堆转储MAT/Eclipse 打开看支配树与 GC Root 链
jstack pid线程栈快照死锁、CPU 飙高、请求卡住
jcmd pid help诊断命令瑞士军刀新工具，能替代大部分 jmap/jstat

图形化/在线工具：JConsole、VisualVM（本地开发）；Arthas（阿里开源，线上免重启看方法耗时/反编译/watch 变量，面试提一句加分）。堆转储离线分析用 MAT：看 Dominator Tree（谁占大头）→ Leaks Suspects → 按 GC Root 找引用链。

常用启动参数：

Shell 
java -Xms4g -Xmx4g \                       # 初始=最大，避免堆动态伸缩抖动
     -Xss512k \                            # 线程栈大小（影响能开的线程数）
     -XX:MaxMetaspaceSize=512m \           # 元空间上限，防动态类生成打爆
     -XX:+HeapDumpOnOutOfMemoryError \     # OOM 时自动留现场
     -XX:HeapDumpPath=/data/dump/ \
     -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \   # G1 与停顿目标
     -jar app.jar
# GC 日志：JDK 8 用 -XX:+PrintGCDetails -XX:+PrintGCDateStamps；
#         JDK 9+ 用 -Xlog:gc*:file=gc.log:time

CPU 飙高排查流程（重点背诵）：top 找到耗 CPU 的 Java 进程 → top -Hp pid 找到线程 → printf '%x\n' tid 把线程号转十六进制 → jstack pid | grep -A 20 'nid=0x???' 定位栈。判读：栈在业务代码 → 看死循环/正则回溯/大量序列化；栈显示 GC 线程多（如 GC task thread）→ 实际是 GC 压力，转内存排查。

内存泄漏排查：jstat 看 Old 区回收后水位只涨不跌 → jmap -histo:live 看异常膨胀的类 → dump + MAT 支配树 → 沿 GC Root 链找到引用持有者。高频泄漏点：静态集合只加不删、ThreadLocal 线程池场景忘记 remove()、资源类未 close、自定义 ClassLoader 缓存。

调优的正确姿势：先有指标（吞吐优先还是延迟优先），再压测拿数据，最后动参数——顺序不能反。常见手段：堆设满物理内存一半左右、对象大导致晋升快就加大 Young 区、Metaspace 报警先查动态代理而非盲目加内存。

二、考点说明

这页在面试里以流程口述题为主：① CPU 飙高五步流程（几乎必考，背熟 top -Hp → 16 进制 → jstack nid）；② 给一个 OOM 报错文案问归因（Metaspace → 动态类生成；heap space → 看是否泄漏）；③ jmap/jstat/jstack 各管什么（选择题配对）；④ 内存泄漏的典型场景（静态集合/ThreadLocal/未关闭资源，能和线程池场景串起来讲）；⑤ 为什么 -Xms=-Xmx。参数细节不用背全，说得出用途和方向即可。

概念自测点击选项即时判分。

单选1. 应用运行一段时间后抛 OutOfMemoryError: Metaspace，最可能的原因是（  ）

A. 堆内存设置太小，直接把 -Xmx 调大一倍
B. 老年代对象太多
C. 动态生成类过多且类加载器无法回收（如大量 CGLIB 代理、Groovy/热部署脚本），元空间被打爆
D. 线程数超过系统上限
答案 C。Metaspace 存类元数据，与堆大小无关——调 -Xmx 没用。先查谁在无限生成类（代理/脚本引擎/热部署），其次才是限制 MaxMetaspaceSize。来源：面试高频改编。

单选2. 用 top 定位到耗 CPU 的 Java 进程 pid=1234 后，下一步最合理的动作是（  ）

A. 立即 jstack 1234 并全文件逐行阅读
B. top -Hp 1234 找到具体耗 CPU 的线程，把线程号转十六进制后到 jstack 输出里按 nid=0x??? 过滤
C. jmap -dump 直接导堆，用 MAT 分析
D. 重启进程恢复服务后再说
答案 B。进程级信息只说明"这个 JVM 忙"，必须下钻到线程；dump 是内存问题的工具，对 CPU 问题信息量低。D 丢失现场，生产上要慎重。来源：牛客经典题。

多选3. 关于 JVM 参数与工具，说法正确的有（  ）

A. -Xms 与 -Xmx 设成一样，可避免堆动态伸缩带来的抖动
B. -XX:+HeapDumpOnOutOfMemoryError 让 OOM 时自动保留堆转储，是提前埋好的"现场"
C. jmap -histo 对线上服务完全无副作用，随便频繁执行
D. jstat -gcutil 可以观察 Old 区回收后水位是否只涨不跌，辅助判断泄漏
答案 ABD。-histo:live 与 dump 前会触发 Full GC，线上大堆执行要挑时机、慎用，C 错。来源：JavaGuide 收录题型。

三、示例题目

口述1. 完整口述「线上服务 CPU 飙到 300%」的排查过程与两种结论分支。

参考回答

① top 确认是哪个 Java 进程；② top -Hp pid 找出最耗 CPU 的线程 TID；③ printf '%x\n' TID 转十六进制；④ jstack pid | grep -A 30 nid=0x??? 看该线程栈。分支一：栈顶是业务代码——看死循环、低效正则回溯、频繁 JSON 序列化等，对应修复；分支二：栈里是 GC 线程（GC task thread 多个占高）——说明 CPU 被 GC 吃掉，转内存方向：jstat -gcutil 看 FGC 频率，jmap -histo 或 dump + MAT 找大对象/泄漏。来源：面试高频改编。

口述2. 运营反馈接口偶发超时，jstat 显示 Old 区 90%+、FGC 一天几十次且回收后水位不降。说排查与处理。

参考回答

水位回收后不降 = 有东西回收不掉，按泄漏查：① jmap -histo:live pid | head 看对象量 Top（byte[]/自定义类异常膨胀往往是线索）；② jmap -dump（挑低峰）+ MAT Dominator Tree 定位占用大头，沿 GC Root 引用链找持有者；③ 常见嫌疑：静态 Map 缓存只加不删、线程池里 ThreadLocal 没 remove（配合内存-sized 大对象）、连接/流未关闭；④ 短期止血可重启或扩容堆，长期按引用链修代码；⑤ 若确认不是泄漏而是"活对象确实大"，再谈加大堆/换 G1/优化缓存淘汰策略。来源：面试高频改编。

计算3. 堆 8G，一次 dump 显示：Young 2G 常满且 YGC 每 30 秒一次、Old 6G 中 4G 是一个 ConcurrentHashMap 的 value（自定义缓存对象），GC 后仍 3.9G。判断问题性质并给两条处理建议。

解答

性质：缓存把老年代占满，接近泄漏（缓存无淘汰或键无限增长）。建议：① 给缓存加容量上限与淘汰策略（如换 Caffeine，maximumSize + expireAfterWrite），杜绝只进不出；② 排查键的生成逻辑（是否把不可控输入直接当键），必要时对 value 做瘦身、用弱引用或分片过期。另：Young 2G 每 30 秒一次 YGC 属正常量级，本轮先别动堆参数。来源：AI 岗笔试高频。

四、易错点小结

① Metaspace OOM 调 -Xmx 无效，方向先找动态类生成；② jstack 过滤线程用 nid=0x十六进制，十进制直接 grep 找不到；③ jmap -histo:live / dump 都会触发 Full GC，线上执行要低峰+授权；④ OOM 排查第一步是看错误类型与 dump 文件，不是重启；⑤ -Xss 太小会 StackOverflow、太大限制总线程数，两面都要会说；⑥ 调优顺序：指标 → 压测 → 改参数，倒过来就是玄学。
