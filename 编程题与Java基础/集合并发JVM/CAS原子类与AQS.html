CAS、原子类与 AQS

适用岗位：测开(Java)、通用软开（并发原理层，追问链终点） ｜ 形态：原理 + 对比 + 模板代码 ｜ 更新：2026-09-30
要点速记：CAS = 内存值 V / 期望值 E / 新值 N，V==E 才写入，CPU 硬件原语保证原子；三大坑：ABA（AtomicStampedReference 版本号解决）、自旋空耗 CPU、只保一个变量（AtomicReference 打包）；LongAdder 分段 Cell 降热点，写多读少最快；AQS = volatile int state + CLH 变体双向等待队列 + 模板方法（tryAcquire 子类实现，失败入队 park 挂起）；公平锁不插队、非公平先 CAS 抢一次；ReentrantLock / CountDownLatch / Semaphore / 读写锁全是 AQS 的壳。

一、知识点梳理

CAS 原理：compare-and-swap，三个操作数——V（内存值）、E（期望值）、N（新值）：仅当 V == E 才把 V 更新为 N，否则失败（自旋重试或放弃）。"比较+交换"由 CPU 硬件原语保证原子（x86 上是 cmpxchg 指令配合 lock 前缀锁缓存行），Java 经 Unsafe 类的 native 方法调用。整个过程线程不阻塞、不加锁。

乐观锁 vs 悲观锁：CAS 自旋 = 乐观锁思想——假设没冲突，失败了重来，适合读多写少、竞争低；synchronized = 悲观锁——先加锁再操作，冲突线程挂起，适合写多竞争高。开销对比：乐观赌赢零开销、赌输空转；悲观无论有无冲突都付出加锁/唤醒成本。

CAS 三大问题：①ABA：值 A→B→A 改回去了，CAS 只比较值相等、察觉不到中间过程（经典场景：无栈链表头指针复用）；解决：AtomicStampedReference 在值之外附加 int 版本戳，每改一次戳变一次，CAS 同时比对值+版本（AtomicMarkableReference 是布尔标记位的简化版）。②自旋长时间失败空耗 CPU：竞争激烈时反复失败白转，缓解：限制自旋次数、竞争高处退回锁。③只能保证一个变量的原子性：对多个变量分别 CAS 不构成整体原子；解决：AtomicReference 把多变量打包成对象引用，一次 CAS 整个对象，或改用锁。

原子类谱系：

类别代表说明
基本类型AtomicInteger / AtomicLong / AtomicBooleanCAS 自旋实现 incrementAndGet 等
引用类型AtomicReference / AtomicStampedReference打包多变量；带版本戳解决 ABA

字段更新器AtomicIntegerFieldUpdater 等反射 CAS 更新 volatile 字段，省包装对象
累加器LongAdder / LongAccumulator / DoubleAdder分段 Cell 计数，写多读少更快

LongAdder 原理：base + Cell[] 数组——无竞争时 CAS base；有竞争时各线程绑定自己的 Cell 累加，把一个热点分散成一排冷点；sum() 汇总 base+所有 Cell，但那是非原子的近似快照。定位：高并发计数（监控统计），不需要精确瞬时值时完胜 AtomicLong；需要"比较并换取结果"（如 ID 生成器）还得 AtomicLong。

i++ 三种线程安全方案对比（i++ = 读-加-写三步，非原子）：

方案原理优点缺点适用
synchronized悲观阻塞最简单可靠加锁唤醒开销最大临界区复杂、竞争极高
AtomicIntegerCAS 自旋无阻塞，中低竞争快高竞争重试成热点需要精确值的计数
LongAdder分段 Cell高并发写最快sum() 非原子快照监控类写多读少计数

AQS（AbstractQueuedSynchronizer）三大件——JUC 锁与同步器的公共骨架：①volatile int state：同步状态，语义由子类定义——ReentrantLock 里是重入次数、Semaphore 里是剩余许可数、CountDownLatch 里是剩余计数；②CLH 变体的双向 FIFO 等待队列：获取失败的线程 CAS 入队，然后 LockSupport.park 挂起自己；前驱释放时 unpark 唤醒后继；③模板方法模式：acquire/release 是固定骨架（CAS 失败→入队→park→醒来重试），tryAcquire/tryRelease（独占）、tryAcquireShared/tryReleaseShared（共享）留给子类实现——写一个同步器只需要决定"state 怎么算拿到/释放"。

独占 vs 共享：独占模式一次只有一个线程持有（ReentrantLock、写锁）；共享模式允许多个线程同时通过（Semaphore 的多个许可、CountDownLatch 放行所有 await、读锁）。

公平 vs 非公平（ReentrantLock 默认非公平）：公平锁——加锁前先检查队列里有没有前驱（hasQueuedPredecessors），有就不抢、乖乖排队，无饥饿但吞吐低；非公平——上来先 CAS 抢一次 state，抢不到才入队，被唤醒后还要再抢一次，吞吐高但可能饥饿。

基于 AQS 的家族：ReentrantLock（独占可重入）、ReentrantReadWriteLock（读共享写独占）、CountDownLatch（共享倒计数）、Semaphore（共享许可）——连线程池的 Worker 内部也继承 AQS 做不可重入的小互斥（见 线程池全解）；CountDownLatch / Semaphore 的使用示例见 ThreadLocal 与并发工具类。ReentrantLock 相比 synchronized 的差异一句：可中断 lockInterruptibly、可超时 tryLock、公平可选、多个 Condition 精准唤醒。

// CAS 原子类计数：100 线程 × 1000 次自增
AtomicInteger counter = new AtomicInteger(0);
Runnable job = () -> {
    for (int j = 0; j < 1000; j++) {
        counter.incrementAndGet();   // CAS 自旋：失败就取最新值重试
    }
};
// 100 个线程各自跑完 job、全部 join 后：counter.get() 恒为 100000

// i++ 三方案对比（面试必背）
synchronized (lock) { count++; }            // 悲观锁：正确但最重
atomicCount.incrementAndGet();              // CAS 自旋：中低竞争性价比高
longAdder.increment();                      // 分段 Cell：高并发写最快，sum() 是快照
Java 
// AQS 视角的极简自定义互斥量（模板方法：只实现 tryAcquire/tryRelease）
class MyMutex extends AbstractQueuedSynchronizer {
    @Override
    protected boolean tryAcquire(int acquires) {
        if (compareAndSetState(0, 1)) {          // state 0→1：CAS 抢锁成功
            setExclusiveOwnerThread(Thread.currentThread());
            return true;
        }
        return false;      // 失败不用管：AQS 骨架负责入队 + park 挂起
    }
    @Override
    protected boolean tryRelease(int releases) {
        if (getState() == 0) throw new IllegalMonitorStateException();
        setExclusiveOwnerThread(null);
        setState(0);       // 释放后：AQS 骨架负责 unpark 唤醒后继节点
        return true;
    }
    public void lock()   { acquire(1); }   // 骨架：tryAcquire 失败 → 入队 → park
    public void unlock() { release(1); }   // 骨架：tryRelease 成功 → 唤醒后继
}

二、考点说明

笔试选择面试口述

  • 面试：i++ 三方案对比、AQS 三大件源码级追问（公平/非公平加锁全流程、独占/共享、park/unpark）、ReentrantLock vs synchronized。

三、示例题目（点击选项即时判分）

单选1. 线程 1 读到值 A 后被挂起；线程 2 把值 A→B 再改回 A；线程 1 恢复后执行 CAS(A→C) 成功。要让它发现"中途变过"，最直接的方案是（  ）

A. 换成 synchronized 包住这次 CAS
B. 使用 AtomicStampedReference，每次修改递增版本号，CAS 同时比对值和版本
C. 把变量改成 volatile
D. 增加 CAS 的重试次数
答案 B。CAS 只比较值相等，A→B→A 会骗过它；AtomicStampedReference 附带 int 版本戳（stamp），改动一次戳变一次，值相同但版本不同照样 CAS 失败。C 的 volatile 只保可见性不保原子判断；D 无济于事——重试多少次值都对得上。来源：面试高频改编。

单选2. 秒级监控系统要统计全局 QPS 计数器：写竞争极高，读只在展示层偶尔发生。最合适的是（  ）

A. AtomicLong，CAS 自旋更新
B. LongAdder，展示时调用 sum()
C. synchronized 保护的 long
D. volatile long 直接自增
答案 B。写竞争极高正是 LongAdder 的主场：分散到 Cell[] 各写各的，消除 CAS 热点；sum() 是非原子快照，但展示场景完全可接受。A 在高竞争下 CAS 重试成热点；D 连原子性都没有，自增必丢更新；C 开销最大。需要精确值或"比较并换"语义时才轮到 AtomicLong。来源：牛客经典题。

多选3. 关于 AQS 的组成，正确的有（  ）

A. 一个 volatile int state，语义由子类定义（重入次数/许可数/剩余计数）
B. CLH 变体的双向 FIFO 等待队列，获取失败的线程入队后 park 挂起
C. 模板方法模式：acquire/release 是骨架，tryAcquire/tryRelease 留给子类实现
D. 内部用一把 synchronized 保护整个等待队列的出入
答案 ABC。三大件 = state + 队列 + 模板方法。D 错——队列的入队出队靠 CAS，挂起与唤醒靠 LockSupport.park/unpark，不是 synchronized 一把大锁。来源：JavaGuide 收录题型。

多选4. CAS 机制自身的问题包括（  ）

A. ABA 问题：值被改回原值后 CAS 无法察觉中间变化
B. 自旋长期失败会空耗 CPU
C. 一次只能保证一个变量的原子性，多变量需要 AtomicReference 打包或加锁
D. CAS 失败会持有资源等待，导致死锁
答案 ABC。D 错——CAS 是非阻塞算法：失败不持有任何锁、不等待任何人，只重试或返回失败，不存在死锁（这是它对比锁的一大优点）。来源：面试高频改编。

单选5. 高并发计数器：写入竞争激烈，只需最终展示总数，读不频繁。最合适的方案是（  ）

A. synchronized 包住 count++
B. AtomicLong.incrementAndGet()
C. LongAdder.increment()，展示时 sum()
D. volatile int count++
答案 C。volatile 不保原子（count++ 三步照丢更新）；竞争激烈时 AtomicLong 的 CAS 重试聚成一个热点；LongAdder 分段写最快，sum() 的快照语义对"展示总数"足够。来源：牛客经典题。

面试口述6. 说说非公平锁（ReentrantLock 默认模式）加锁的完整流程。

参考回答①CAS 尝试把 state 从 0 改 1：抢到 → setExclusiveOwnerThread 记录持有者，直接返回（这一步就是"插队"——不管队列里排没排人）；②state ≠ 0 但持有者是自己 → 重入，state 加 1 返回；③都不是 → 加锁失败，addWaiter 把自己包装成节点 CAS 挂到 CLH 队尾，然后 acquireQueued：若前驱是队头哨兵就再试一次抢锁，否则 park 挂起自己；④前驱释放锁时 unpark 唤醒后继，醒来后再 CAS 抢一次（这里又可能被新来的线程抢先——非公平的第二处插队）。公平锁的唯一区别：每次抢之前先 hasQueuedPredecessors() 查队列，有前驱就不抢。来源：面试高频改编。

四、易错点小结

① CAS 三操作数背全：V 内存值 / E 期望值 / N 新值，少说一个都算没背；② ABA 的题眼是"值变回来了"，答案锁定版本号（AtomicStampedReference）；③ LongAdder 快的代价：sum() 是非原子快照，需要精确值/比较换语义用 AtomicLong；④ AQS 三大件 + park/unpark 一个都不能少，"state 语义由子类定义"是关键句；⑤ 非公平锁"插队"有两处：第一次 CAS 和被唤醒后的再 CAS。
