线程基础与 synchronized

适用岗位：测开(Java)、通用软开 ｜ 形态：概念 + 状态机 + 输出判断 + 机试手写 ｜ 更新：2026-09-30
要点速记：sleep 不放锁是 Thread 静态方法，wait 放锁是 Object 方法、必须在同步块内调用；synchronized 实例方法锁 this、静态方法锁 Class 对象、代码块锁括号里指定的对象；volatile 保证可见性、禁止指令重排，但不保证 i++ 这类复合操作的原子性；锁升级单向：无锁→偏向→轻量级→重量级；生产者消费者里 wait 的条件判断必须用 while 防虚假唤醒。

一、知识点梳理

创建线程的四种方式

  • ① 继承 Thread 重写 run：单继承受限，任务和线程耦合，不推荐。
  • ② 实现 Runnable：任务与执行解耦，无返回值、不抛受检异常——比继承 Thread 好。
  • ③ 实现 Callable<V> + FutureTask：有返回值、可抛异常，get() 阻塞拿结果。
  • ④ 线程池（生产推荐）：复用线程、控制并发数、统一管理。阿里规约禁用 Executors 快捷工厂——newFixedThreadPool 是无界队列、newCachedThreadPool 可无限加线程，都有 OOM 风险，要求手动 new ThreadPoolExecutor(...)。
Java 
// ① 继承 Thread
class MyThread extends Thread {
    @Override public void run() { System.out.println("A"); }
}
new MyThread().start();

// ② 实现 Runnable：任务与执行解耦，无返回值
Runnable r = () -> System.out.println("B");
new Thread(r).start();

// ③ Callable + FutureTask：有返回值、可抛异常
Callable<Integer> c = () -> 1 + 1;
FutureTask<Integer> ft = new FutureTask<>(c);
new Thread(ft).start();
System.out.println(ft.get());   // 阻塞等待执行完成，输出 2

// ④ 线程池：生产推荐，手动指定参数
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        2, 4, 60, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(100),
        new ThreadPoolExecutor.AbortPolicy());
pool.execute(r);

    NEW --> RUNNABLE: start()

    WAITING --> RUNNABLE: notify() / unpark() 后抢到锁

    RUNNABLE --> TERMINATED: run() 执行完 / 未捕获异常
  • NEW：new 出线程对象还没 start()。
  • RUNNABLE：start() 之后；Java 把操作系统的"就绪 + 运行中"合并成一个状态。
  • BLOCKED：等 monitor 锁——进 synchronized 没抢到；wait 被唤醒后重抢锁也是它（javadoc 口径，面试加分点）。
  • WAITING：无限等待，等别人叫：无参 wait()、无参 join()、LockSupport.park()。
  • TIMED_WAITING：限时等待，到点自己醒：sleep(n)、wait(n)、join(n)、parkUntil(n)。
  • TERMINATED：run() 执行完或抛出未捕获异常；终态不可逆，再次 start() 抛 IllegalThreadStateException。

synchronized 三种用法与 monitor 原理

Java 
public class Locker {
    private final Object lock = new Object();
    private int count;

    // ① 实例方法：锁当前实例 this
    public synchronized void inc() { count++; }

    // ② 静态方法：锁类对象 Locker.class（类锁，全局只有一把）
    public static synchronized void reset() { /* ... */ }

    // ③ 同步代码块：锁括号里指定的对象
    public void dec() {
        synchronized (this) {           // 等价于 ①
            count--;
        }
        synchronized (lock) {           // 私有锁对象：外部拿不到引用，锁不被干扰
            count++;
        }
        synchronized (Locker.class) {   // 等价于 ②
            /* ... */
        }
    }
}
  • 实例方法锁 this、静态方法锁 Class、代码块锁指定对象——实例方法与静态方法不互斥（锁的不是同一个对象），这是经典坑。
  • 对象头 Mark Word：存 hashCode、GC 分代年龄、锁标志位；加锁后存线程 ID 或指向 Lock Record / monitor 的指针。
  • 字节码层面：同步代码块编译成 monitorenter / monitorexit（异常出口也有一条 monitorexit 保证解锁）；同步方法靠 ACC_SYNCHRONIZED 标志由 JVM 隐式加解锁。
  • monitor（ObjectMonitor）：owner 记持有线程，entryList 是抢锁阻塞队列，waitSet 是 wait 后的等待队列。

锁升级（JDK6 引入；JDK15 起默认废弃偏向锁，JEP 374——版本结论要带年份说）

  • 无锁 → 偏向锁：只有一个线程反复进入，Mark Word 直接记线程 ID，再次进入零成本；出现第二个线程竞争就撤销。
  • 偏向锁 → 轻量级锁：线程交替竞争（没有同时抢），CAS 自旋获取，线程不挂起。
  • 轻量级锁 → 重量级锁：竞争激烈、自旋不划算时膨胀为 monitor，抢不到的线程挂起，涉及用户态/内核态切换。
  • 升级单向不可降级。一句话：竞争从无到有逐级加码。

volatile：两个作用、一个不保

  • 保证可见性：写 volatile 变量立即刷回主存并使其他核心的缓存副本失效，读时从主存加载——一个线程的修改其他线程立刻可见。
  • 禁止指令重排：靠内存屏障，典型应用是双检锁单例防"半初始化对象"。
  • 不保证原子性：i++ 是"读→加→写"三步，volatile 挡不住线程交错，仍会丢更新；要原子性用 synchronized 或 AtomicInteger.incrementAndGet()。
Java 
public class LostUpdate {
    private static volatile int count = 0;   // volatile 也救不了 i++

    public static void main(String[] args) throws InterruptedException {
        Runnable r = () -> {
            for (int i = 0; i < 10000; i++) count++;
        };
        Thread t1 = new Thread(r), t2 = new Thread(r);
        t1.start(); t2.start();
        t1.join(); t2.join();
        System.out.println(count);           // 几乎每次都小于 20000（如 13472）
        // 修复：synchronized 包住 count++，或改用 AtomicInteger.incrementAndGet()
    }
}

双检锁单例（volatile + synchronized 的合体考点）

Java 
public class Singleton {
    private static volatile Singleton instance;   // volatile 必须加，防重排
    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查：多数调用免加锁
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次检查：等锁期间可能已被创建
                    instance = new Singleton();    // 分配内存→初始化→赋引用，可能被重排
                }
            }
        }
        return instance;
    }
}

synchronized vs ReentrantLock

对比点synchronizedReentrantLock
层面JVM 关键字（monitor）JDK API（AQS 实现）
释放锁自动释放（异常也释放）必须 finally 里 unlock()
可中断不可，等锁时死等lockInterruptibly() 可中断

tryLock没有有，可限时尝试拿锁

选型一句话：默认 synchronized（简洁、不易错）；需要可中断、限时、公平、多条件时才上 ReentrantLock。

wait/notify 生产者消费者极简范式

Java 
class BoundedBuffer {
    private final Queue<Integer> buf = new ArrayDeque<>();
    private final int cap = 10;

    public synchronized void put(int v) throws InterruptedException {
        while (buf.size() == cap) wait();   // 必须 while 不用 if：防虚假唤醒
        buf.add(v);
        notifyAll();                        // 唤醒所有等待者，条件不满足的继续回去等
    }

    public synchronized int take() throws InterruptedException {
        while (buf.isEmpty()) wait();       // 被唤醒后条件可能已被别人抢走，重新判断
        int v = buf.poll();
        notifyAll();
        return v;
    }
}

Python 对照

Python 
import threading

lock = threading.Lock()
counter = 0

def add():
    global counter
    for _ in range(100000):
        with lock:            # with 自动获取/释放，对应 synchronized(对象)
            counter += 1

t1 = threading.Thread(target=add)
t2 = threading.Thread(target=add)
t1.start(); t2.start()
t1.join(); t2.join()
print(counter)                # 100000

# 语义差异：Java synchronized 保护多线程共享的堆对象；CPython 有 GIL，
# 同一时刻只有一个线程执行字节码，但 += 仍是"读-改-写"多步操作，
# 线程随时可能切换，锁照样不能省。多线程适合 IO 密集，CPU 密集用
# multiprocessing；GIL 细节见 Python 进阶页对应主题。

三、示例题目（点击选项即时判分）

单选1. 线程 T 已获得锁并在 synchronized 块内调用了 lock.wait()（无参），此时 T 处于什么状态？

A. BLOCKED，等待重新获得锁
B. WAITING，无限期等待被唤醒
C. TIMED_WAITING，限时等待
D. RUNNABLE，继续占用 CPU
答案 B。无参 wait() → WAITING；wait(n)/sleep(n) 才是 TIMED_WAITING。加分点：T 已在 wait 时释放了锁；被 notify 唤醒后按 javadoc 先回 BLOCKED 重抢锁，抢到才回 RUNNABLE。来源：牛客经典题。

多选2. 关于 sleep 与 wait，正确的有（  ）

A. sleep 是 Thread 的静态方法，wait 是 Object 的成员方法
B. sleep 不释放已持有的锁，wait 释放对象锁
C. wait 可以在任意位置直接调用
D. 无参 wait() 只能被 notify/notifyAll（或中断）唤醒
答案 ABD。C 错——wait 必须在持有该对象锁的 synchronized 块内调用，否则抛 IllegalMonitorStateException；这也是"wait 放锁、sleep 不放锁"的前提。来源：牛客经典题。

多选3. 关于 volatile，说法正确的有（  ）

A. 对 volatile 变量的写操作立即对其他线程可见
B. 通过内存屏障禁止指令重排
C. volatile int count; 多线程执行 count++ 是线程安全的
D. 典型用途：双检锁单例的实例引用、线程可见的状态标志位
答案 ABD。C 是最经典的坑——count++ 是读→加→写三步，volatile 不保证原子性，交错执行仍丢更新；要原子性用 AtomicInteger 或加锁。来源：JavaGuide 收录题型。

输出判断4. 以下代码，线程 A 调 p.printA()、线程 B 调 p.printB()，同时启动，总耗时约（  ）

class Printer {
    public synchronized void printA() throws InterruptedException {
        Thread.sleep(1000);
    }
    public static synchronized void printB() throws InterruptedException {
        Thread.sleep(1000);
    }
}
Printer p = new Printer();
A. 约 1 秒：printA 锁 p（实例），printB 锁 Printer.class（类），锁的不是同一个对象，不互斥
B. 约 2 秒：所有 synchronized 方法互相排斥
C. 编译报错：实例方法与静态方法不能都加 synchronized
D. 无法确定，取决于 JVM 调度
答案 A。实例方法锁的是当前实例，静态方法锁的是 Class 对象，两把不同的锁，可并行。若两个线程都调 p.printA() 才是约 2 秒。延伸：换成两个不同实例分别调 printA 也互不相干。来源：面试高频改编。

面试口述5. 描述 synchronized 锁升级的完整流程。

参考回答对象初始为无锁。第一次被线程访问时升级为偏向锁：Mark Word 记下线程 ID，之后同一线程再进入无需任何同步操作；一旦有第二个线程竞争，偏向锁撤销，升级为轻量级锁：线程用 CAS 自旋抢锁，适合线程交替、持有时间短的场景；自旋失败或竞争激烈（同时抢、持有时间长）就膨胀为重量级锁：依赖操作系统 mutex，抢不到的线程挂起，有用户态/内核态切换开销。整个过程单向升级、不可降级。版本分寸：锁升级是 JDK6 引入的优化；JDK15 起偏向锁默认废弃（JEP 374，维护成本高、收益在现代场景下降），新代码谈锁升级要带这句。加分点：Mark Word 各阶段的位布局、自适应自旋。

四、易错点小结

① start() 才会开新线程，直接调 run() 是当前线程里的普通方法调用；线程 TERMINATED 后再 start() 抛 IllegalThreadStateException。② wait/notify 必须持有该对象锁才能调，否则 IllegalMonitorStateException；wait 的条件判断必须用 while（防虚假唤醒、防唤醒后条件已变）。③ sleep 在同步块内不释放锁，别拿 sleep 当"让锁"用。④ 别拿字符串字面量或 Integer 缓存对象当锁（synchronized ("abc")）——常量池/缓存让不相干代码共享同一把锁。⑤ volatile 计数器是经典错误，原子性找 AtomicInteger 或加锁。⑥ 双检锁单例漏 volatile 会在重排下返回半初始化对象。
