ConcurrentHashMap 与线程安全集合

适用岗位：测开(Java)、通用软开（承接 HashMap 的固定第二问） ｜ 形态：原理 + 对比表 + 手写 LRU ｜ 更新：2026-09-30
要点速记：HashMap 并发不安全（1.7 头插扩容成环 / 1.8 覆盖丢数据）→ JDK7 分段锁 Segment（默认并发度 16）、JDK8 CAS + synchronized 锁桶头节点（粒度到单个桶）；key/value 都不允许 null（并发 get 二义性）；size 用 baseCount + CounterCell 分散热点（LongAdder 思想）；读多写极少用 CopyOnWriteArrayList；LRU = LinkedHashMap(accessOrder=true) + removeEldestEntry，或手写哈希表 + 双向链表（get/put O(1)）。

一、知识点梳理

为什么 HashMap 不能用于并发（细节见 HashMap 全解）：JDK7 头插法在两线程同时扩容迁移时指针交错形成环，get 死循环 CPU 100%；JDK8 改尾插不成环，但并发 put 仍会覆盖丢失数据。所以并发场景必须换 ConcurrentHashMap（下称 CHM）。

JDK7：分段锁 Segment：整个表被拆成多个 Segment（每段继承 ReentrantLock，锁原理见 CAS、原子类与 AQS），每段管一小片桶数组；默认并发度 16（即默认 16 段，指定值会向上取 2 的幂），不同 Segment 的写操作互不阻塞——并发度就是"最多多少线程同时写"。

JDK8：CAS + synchronized 锁桶头节点：放弃分段，回到大数组 + 单桶粒度：锁的粒度细到单个桶的头节点，冲突概率极低；读操作完全无锁（Node 的 val/next 是 volatile，保证可见性）。

JDK8 put 流程（面试背诵版）：①计算 hash（(h ^ (h >>> 16)) 扰动，与 HashMap 同源）→ ②table 未初始化则 initTable()（CAS 把 sizeCtl 置 -1 抢初始化权，其他线程自旋让步）→ ③目标桶为空：CAS 插入新节点，失败说明有竞争，进入下一轮循环 → ④桶头是 ForwardingNode（hash = MOVED = -1，标记"该桶已迁移"）：说明正在扩容，helpTransfer 协助迁移后重试 → ⑤否则 synchronized 锁住头节点，链表尾插或红黑树插入 → ⑥链表长度 ≥ 8 且容量 ≥ 64 树化（与 HashMap 同规则）→ ⑦addCount 更新计数并检查是否触发扩容。

sizeCtl 一句话：多用途控制字——-1 表示正在初始化；其他负数表示有线程正在扩容（编码了参与线程数）；正数表示下次扩容阈值（容量×0.75）。

size 怎么计数：没有一把大锁保护单个计数器，而是 baseCount + CounterCell[]：无竞争时 CAS 更新 baseCount；CAS 失败（有热点）就分散到各自的 CounterCell 累加——正是 LongAdder 的思想；size() 汇总 base + 所有 Cell，返回的是近似精确值。

为什么 key/value 都不允许 null：并发下 get(key) 返回 null 有二义性——"键不存在"还是"值就是 null"？单线程 HashMap 可以"先 containsKey 再 get"区分，但并发下这两步之间状态可能被其他线程改掉，区分失效。索性禁止 null，把二义性扼杀在 API 层面。HashMap 允许一个 null 键、CHM 直接抛 NPE，是两者最常考的差异点。

Collections.synchronizedMap vs CHM：

CopyOnWriteArrayList（写时复制）：写操作（add/set/remove）先复制一份新数组，在新数组上改，再 volatile 引用替换——读完全无锁；代价：写要整份拷贝、开销大；一致性弱：迭代器持有旧数组快照，遍历时读不到别人的新写（也因此不抛 CME）。定位：读极多、写极少的场景（白名单、监听器列表、配置缓存）。

LinkedHashMap 做 LRU：构造参数 new LinkedHashMap<>(16, 0.75f, true) 第三个参数 true = 开启访问序（get 也会把节点挪到链表尾）；再重写 removeEldestEntry(eldest) 返回 size() > capacity，即可自动淘汰链表头（最久未使用）。

TreeMap / Hashtable 一句话：TreeMap 红黑树按 key 排序、非线程安全（键需可比较）；Hashtable 全表 synchronized、key/value 不许 null、被 CHM 完全取代，如今只剩笔试"线程安全归类"价值。

Java 
// LRU 缓存第一版：LinkedHashMap 三行核心（面试先给这个，再问手写）
class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LruCache(int capacity) {
        super(16, 0.75f, true);        // true = 按访问序：get 也把节点挪到尾部
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;      // 超容量淘汰链表头（最久未使用）
    }
}

// LRU 缓存第二版：手写哈希表 + 双向链表（哨兵头尾），get/put 均 O(1)——LeetCode 146 标准写法
class LRUCache {
    private final int cap;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0), tail = new Node(0, 0);  // 哨兵

    private static class Node {
        int key, val; Node prev, next;
        Node(int k, int v) { key = k; val = v; }
    }

    LRUCache(int capacity) { cap = capacity; head.next = tail; tail.prev = head; }

    public int get(int key) {
        Node n = map.get(key);          // 哈希表 O(1) 定位链表节点
        if (n == null) return -1;
        unlink(n); addToTail(n);        // 挪到尾部 = 最近使用
        return n.val;
    }
    public void put(int key, int value) {
        Node n = map.get(key);
        if (n != null) { n.val = value; unlink(n); addToTail(n); return; }
        if (map.size() == cap) {        // 淘汰链表头部 = 最久未使用
            Node oldest = head.next;
            unlink(oldest); map.remove(oldest.key);
        }
        Node fresh = new Node(key, value);
        map.put(key, fresh); addToTail(fresh);
    }
    private void unlink(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void addToTail(Node n) {    // 挂到 tail 哨兵之前
        n.prev = tail.prev; n.next = tail;
        tail.prev.next = n; tail.prev = n;
    }
}

三、示例题目（点击选项即时判分）

多选1. 关于 ConcurrentHashMap 的锁设计，正确的有（  ）

A. JDK7 以 Segment 为锁单位（默认 16 段，继承 ReentrantLock），不同段可同时写
B. JDK8 改用 CAS + synchronized，锁的是桶的头节点，粒度细到单个桶
C. JDK8 对整个 Node 数组加一把大锁，读操作也要排队
D. JDK8 完全无锁化，任何写操作都不需要任何同步手段
答案 AB。演进主线就是锁粒度不断变细：全表锁（Hashtable）→ 段锁（1.7）→ 桶头锁（1.8）。C 错——锁到桶头且读无锁；D 错——写仍需 CAS 或 synchronized 保证原子，只是冲突概率极低。来源：面试高频改编。

单选2. ConcurrentHashMap 的 key 和 value 都不允许为 null，最主要的原因是（  ）

A. null 键无法计算 hashCode，会抛空指针异常
B. 并发下 get 返回 null 存在二义性：无法区分"键不存在"与"值就是 null"，而 containsKey+get 两步在并发下不具原子性
C. 为了与 Hashtable 的 API 保持完全兼容
D. 为了减少内部节点的内存占用
答案 B。这是官方设计取舍：单线程 HashMap 靠"先 containsKey 再 get"能区分二义性，并发下两步之间状态可能被改，区分失效，索性禁止。A 是表象不是原因——HashMap 就对 null 键做了特判（hash 恒为 0），特判同样可行。来源：面试高频改编。

单选3. 场景：一份白名单/监听器列表，读取极其频繁，修改偶尔发生，要求读操作不被阻塞。最合适的是（  ）

A. Vector
B. Collections.synchronizedList 包装的 ArrayList
C. CopyOnWriteArrayList
D. LinkedList
答案 C。写时复制 + volatile 引用替换，读完全无锁且不被写阻塞，正是"读极多写极少"的标准答案。代价：写要整份拷贝、迭代器是旧数组快照（读不到最新写，但不会抛 CME）。A/B 读也要抢锁；D 线程不安全。来源：牛客经典题。

单选4. JDK8 中 ConcurrentHashMap 统计元素个数（size）的实现方式是（  ）

A. 维护一个 volatile int size，每次 put 直接自增
B. baseCount + CounterCell 数组分散计数热点（LongAdder 思想），size() 时汇总
C. 每次调用 size() 时遍历所有桶逐个数
D. 用一把全局锁保护一个计数器，计数时必须持锁
答案 B。无竞争时 CAS 更新 baseCount；CAS 失败说明有热点，改写各自绑定的 CounterCell；size() = base + 所有 Cell 求和。这与 LongAdder 的设计一模一样——分散写热点，代价是结果为近似精确的快照。来源：JavaGuide 收录题型。

面试口述5. 手写一个 LRU 缓存：选什么数据结构？为什么？get/put 复杂度是多少？

参考回答数据结构：哈希表 + 双向链表。哈希表负责 O(1) 定位到链表节点；双向链表维护"最近使用"顺序，尾部是最新、头部是最久未用。为什么必须双向：淘汰/挪位要 O(1) 摘除任意节点，单链表删节点得先找前驱，是 O(n)。操作：get 命中就把节点挪到尾并返回值；put 已存在则更新并挪尾，不存在且满了就摘掉头节点再插尾。两者整体 O(1)。加分点：哨兵头尾节点简化边界；LinkedHashMap(accessOrder=true) + removeEldestEntry 三行库法版；Java 里还可以说"链表节点存 key 是为了淘汰时反查哈希表删除"。来源：面试高频改编。

四、易错点小结

① 锁粒度演进一句话背：Hashtable 全表 → JDK7 段（默认 16）→ JDK8 桶头；② CHM 的"线程安全"只保证单个操作原子，"先 get 判断再 put"这类复合操作要用 putIfAbsent / computeIfAbsent；③ CopyOnWriteArrayList 一致性弱：迭代器是快照，读不到新写；④ LRU 的双向链表不是装饰——单链表删节点要 O(n) 找前驱；⑤ key/value 禁 null 是 CHM 与 HashMap 最常考差异，题眼就是"二义性"。
